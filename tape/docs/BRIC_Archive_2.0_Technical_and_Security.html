1Document control and scope

This document describes how BRIC Archive 2.0 works, in full, from the moment a researcher logs in to the moment data is recovered from tape fifteen years later. It is written for two audiences at once: a security reviewer who needs to judge the controls, and a management reader who needs to understand what the system guarantees and what it deliberately does not.

1.1What is in scope

The software described here is the BRIC Archive 2.0 system: the user-facing command-line interface, the backup producer, the staging protocol, the tape server daemon, the restore path, the disaster-recovery tooling, the installation and update machinery, the logging subsystem and the test suite. The physical library, the QNAP staging appliance, the Isilon source storage and the two host operating systems are described where the software depends on their behaviour, but they are managed outside this system.

1.2What is out of scope

  • Legal advice. Sections that touch on retention, deletion and personal data describe technical behaviour only; they are not a data-protection assessment and should be read alongside one, not instead of one.
  • Network and endpoint security of the two hosts, the campus network, and SSH access control. BRIC Archive relies on those controls and does not replace them.
  • The tape library vendor's firmware and robotics. An open vendor case exists (see §17.2); BRIC's behaviour in the presence of a faulty changer is described, the fault itself is not.

1.3Terminology conventions

Throughout this document, chunk means one unit of archived payload; segment means one physical copy of a chunk on one cartridge; run means one invocation of bric backup; marker means a small file on the shared staging directory used as a message between the two hosts. A full glossary is in Appendix D.

1.4Statements of confidence

Everything stated as system behaviour in sections 3 to 16 is derived from the current source code and is verifiable against it. Section 17 distinguishes between what the code implements and what has been demonstrated through automated tests and real-hardware validation. Where evidence differs in scope, the distinction is made explicit rather than merged into a single claim.

2Executive summary

BRIC Archive 2.0 is an archive, not a backup system. The distinction is the whole design. A backup is judged by how quickly it restores into an existing environment. An archive is judged by whether the data can still be read when the environment is gone. BRIC's promise is specific and testable:

The promise

Genomic data written by BRIC Archive must be recoverable in ten to fifteen years from the tapes and one key alone — with no cluster, no central catalogue, no daemon, no QNAP appliance, and without BRIC or the University still operating the system that wrote them.

Everything else in the system is the cost of keeping that promise honest. The consequences, in brief:

  • Each closed archive carries the metadata needed to verify and recover every chunk independently. The chunk payload is ciphertext; the encrypted project catalogue carries the per-chunk HMAC and file map, while the cartridge carries the plaintext TOC and recovery kit. Recovery does not require the central BRIC databases.
  • Every chunk in a successfully closed run has two verified physical copies, on the PRIMARY and BACKUP cartridges of a matched pair. During production a run can temporarily have zero, one or two completed copies; CLOSED is the barrier that guarantees both.
  • No tape write is accepted as verified until it has been read back and re-hashed. A run is only reported as complete when both copies, all recovery artefacts and the tables of contents required by the close protocol have been written and read-back-verified, and the media-release barrier has completed.
  • The tape server never holds a data-decryption key. It moves opaque ciphertext. It does hold its own bus-signing private key, which authenticates tape-side protocol receipts but cannot decrypt research data. A root compromise of the tape host therefore preserves confidentiality but does not preserve protocol integrity or availability.
  • Each researcher has an individual data-encryption key. The operational key is stored in the user’s protected ~/.bric area on the KU-managed cluster at mode 0600; a user-held copy is delivered on dedicated USB media. The institution stores an authenticated escrow copy wrapped under the master key. The tape server never receives a data-decryption key.
  • Data confidentiality survives media loss. A cartridge lost in transit to the off-site location discloses nothing without the corresponding user key.
  • Restore has two independent outcomes: data integrity and metadata fidelity. File contents are verified against the archive independently of permissions, ACLs and extended attributes. A destination may be able to receive and verify every byte while being unable to reproduce historical access-control metadata. In that case BRIC must report the data as verified and the metadata fidelity as degraded; it must never describe the restore as full-fidelity merely because the files are readable.

The operational picture for management is equally short. A researcher runs one command, bric backup PROJECT /path, and can log out; local-mode jobs detach and survive the session. Tape capacity is reserved before ciphertext production. The default local producer uses four parallel data workers inside one project/run and 128 GB decimal chunks, while the tape service still requires two verified physical copies before a chunk is complete. Progress, failures and completions are recorded in structured operational logs and catalogue audit records. The current source tree defines an 82-test standard software gate; the packaged validation record distinguishes focused development validation from the independent native gate and from real-hardware evidence, as described in §17.

3Design thesis and invariants

3.1The recoverability promise

The architecture document that governs this codebase opens with a single thesis: this is an archive, and a feature that does not serve the recoverability promise or fix a concrete observed failure is not an addition but weight. That rule is enforced culturally through code review, and it explains several deliberate absences in the system — there is no deduplication, no incremental-diff engine, no compression, no second implementation of any mechanism, and no optional hardening that is on by default.

3.2The ten load-bearing invariants

Correctness rests on ten invariants. They are few on purpose: if one is broken the system is broken regardless of everything else, so each is separately testable.

#InvariantWhat it buys
I1Claim is an atomic rename. Taking a chunk off the staging bus is a rename() from .READY to .CLAIMED.Exactly one winner, with no distributed lock manager.
I2One active run per project, enforced by a conditional insert inside an explicit write transaction.Two concurrent backups of the same project cannot coexist.
I3Each chunk is independently recoverable with its project metadata and key. The ciphertext is separately hashed and MACed; the encrypted project catalogue records the HMAC, file map and crypto parameters, and the tape TOC records placement and ciphertext SHA-256.No data dependency on another chunk; recovery can fall back copy-by-copy and chunk-by-chunk.
I4Tape is append-only and project-scoped. The index is never rewritten; each close appends a new cumulative table of contents built only from verified rows.No in-place mutation of media; the newest valid index wins.
I5Two copies, PRIMARY and BACKUP, on the two cartridges of a registered pair; restore and disaster recovery try primary then fall back to backup.Transparent self-healing against single-media failure.
I6Encrypt-then-MAC. The HMAC over the ciphertext is verified before anything is handed to openssl or tar.No blind decryption of a tampered or forged blob; path traversal and parser attacks are stopped upstream.
I7Singleton plus generation fence plus recovery. One daemon at a time; a surviving worker from an older generation must exit before the new one touches catalogue or hardware.No two processes driving the same library or catalogue.
I8The central catalogue is not the only truth. Every tape carries its own recovery kit and encrypted project catalogue; the tape catalogue is rebuildable from the media.Database loss is an inconvenience, not a data loss.
I9The format is fixed and versioned. Cryptographic parameters are pinned and recorded; markers, index and kit all carry version tags.A future V2 can evolve without making V1 tapes unreadable.
I10No transition without a durable trace. Every process and hardware phase emits structured events; with BRIC_REQUIRE_LOGGING=1 the system refuses to start if it cannot log.A backup whose operational history cannot be reconstructed is not accepted.

3.3Complexity control rule

New functionality must attach either to one of the invariants above — making it explicit or more robust — or to a concrete, observed operational failure. Two corollaries are enforced strictly, both after real incidents:

  • Never a second implementation of the same mechanism. A duplicate restore script that had grown alongside the canonical disaster-recovery tool was deleted, because two nearly identical things diverge and the bug appears exactly at the point of divergence.
  • Compatibility defaults must not be mistaken for production policy. Bus signing is optional at schema level for upgrade compatibility, while the production role configuration and setup path intend it to be mandatory once keys are present. The post-deploy catalogue value therefore has to be verified explicitly; a schema default of 0 is not a statement that unsigned operation is an acceptable production posture.

4.3Data-flow overview

ISILON (OneFS/NFS — accessible only from the KU cluster environment) | | source preflight + exact included-scope manifest | default local mode: 4 parallel GNU tar streams | -> bric-tar-stream -> AES-256-CBC -> SHA-256 + HMAC v QNAP /bric/archive/<project>/<run_id>/ <-- encrypted staging bus chunk_NNNN.enc (+ .sha256, .hmac, .meta) READY -> CLAIMED -> DONE | ERROR | | tape server polls; it has no ISILON mount and no user data-decryption key v TAPE SERVER (mtx + mt + dd) -> 2 verified copies per chunk -> PRIMARY + BACKUP -> streaming read-back byte/hash verification Restore uses the same bus in reverse with progressive one-chunk backpressure: request -> signed PROGRESS -> chunk.READY -> chunk.CONSUMED -> ... -> request.STAGED The tape server returns opaque ciphertext; authentication, decryption, placement and final destination verification happen on the cluster side.

Three properties of this flow matter to a reviewer. First, the tape server has no direct access to ISILON: archive work originates in the KU cluster environment and the tape side only polls the staging bus. Second, payload bytes that cross into the tape zone are already encrypted. The bus is not metadata-free — project/run identifiers, owner fields, sizes, hashes, timing and protocol state are visible — but archived file paths and plaintext contents remain on the cluster side or inside the encrypted project catalogue. Third, the producer may use several source streams concurrently, but every regular file belongs to exactly one worker and all workers publish into one global chunk namespace for the same run.

4.4The two catalogues

There is deliberately no shared database. Two SQLite catalogues exist, each authoritative for its own phase, both in WAL mode and both on local storage — never on a network filesystem.

Cluster catalogue (cluster_catalog.db) — authoritative for the data phase
Holds configuration, users and authenticated key escrows, projects, runs, chunks, the per-file map, reservations, project/tape convenience mappings, audit records, exclusions and source-consistency records. Run records also carry the canonical source path and stable logical_root. File records contain relative path, size, mtime, plaintext SHA-256, chunk/member mapping and entry type; current rows can additionally carry ordinary regular-file mode and a versioned metadata envelope used for LARGE_FILE_CHUNK ACL/xattr fidelity.
Tape catalogue (tape_catalog.db) — authoritative for the physical phase
Holds cartridges, project assignment, reservations, physical segment placement, verification state, close artefacts, capacity/wear counters, health state and physical audit records. It contains no archived file-path map and no user data-decryption key.

Privacy note. The cluster catalogue contains archived file names and plaintext file checksums and must therefore be treated as sensitive metadata within the KU-managed cluster environment. The QNAP staging bus does not carry the file-to-chunk map. On tape that map exists only inside catalog_project.enc, encrypted under the owner’s key.

4.5Infrastructure assumptions

Two assumptions are load-bearing and are stated explicitly because they are properties of the environment rather than of the code.

Assumption 1 — POSIX semantics on the shared export

The bus protocol depends on three properties of the QNAP NFS export: atomic rename() (the chunk claim is a rename; there must be exactly one winner), coherent cross-host visibility (a file created by one host is immediately and completely visible to the other), and no incoherent caching (no stale reads). These hold for the export as configured. They are not guaranteed by an arbitrary network share; an NFS setup with aggressive attribute caching, or an implementation that does not preserve the expected rename semantics within one export, would violate them. Marker signing protects against forgery and relocation — it does not protect against filesystem incoherence.

Assumption 2 — source quiescence

Archiving should be done from a snapshot or from frozen data. In the tar-driven local mode GNU tar is the authoritative reader and the catalogue describes what tar actually read, so there is no long window between planning and production. If a file changes while tar is reading it, the default policy (source_change_policy=strict) aborts the run rather than closing a silent mix of versions. An explicit record policy exists for live trees and is described in §9.7.

5Threat model

The controls in this system were chosen against a specific set of adversaries and accidents. Stating them makes it possible to judge both what is defended and what is knowingly not.

The tape carries no usable key: the escrow artefact on tape is itself ciphertext under the institution master key, which is never written to tape. Metadata leakage limited to the plaintext table of contents: barcode, run identifiers, project name, chunk numbers, file numbers and hashes. No file names, no data.

6Identity, accounts and authorisation

6.1Host login and the absence of an application login

BRIC Archive has no application-level login, no password of its own and no independent identity store. The authentication boundary is the KU-managed host environment. A researcher must hold a valid KU identity, connect through the KU VPN and authenticate to the designated cluster gate host. BRIC then uses the operating-system identity resolved through the University infrastructure (NSS/SSSD/Active Directory).

Source-data access remains governed by the filesystem permissions, Unix groups and ACLs assigned through KU and the relevant research project. BRIC Archive does not grant additional access to ISILON data.

The installed command loads a managed ~/.bric/env.sh. User provisioning creates a protected ~/.bric directory and stores the personal archive key there at mode 0600, owned by that user. The key therefore remains inside the KU-managed cluster security boundary and is never stored on the tape server. A separate user-held copy may be issued on dedicated USB media under the onboarding procedure in §6.7.

6.2Identity resolution and impersonation resistance

All ownership decisions call one function. It resolves the effective identity as follows:

  1. If BRIC_USER is unset: the real OS account (id -un), except that root invoking through sudo resolves to SUDO_USER.
  2. If BRIC_USER is set: it is honoured only when it equals the real OS account, or the caller is root (UID 0), or the explicitly trusted override BRIC_ALLOW_USER_OVERRIDE=1 is set — a switch used by controlled test and service workflows.
  3. Otherwise the override is ignored, a warning is logged, and the real OS account is used.

The practical consequence is that exporting BRIC_USER=someone_else does not let an unprivileged user act as another archive owner. Even if the identity check were bypassed, the attempt would fail at the next step, because the other user's key lives in their own home at mode 0600.

Project and owner names are additionally constrained by a strict charset — ^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$ — because these strings become path components on the shared export where SQL escaping offers no protection. The rule rejects slashes, spaces, control characters, leading dots or dashes, and ...

Long-term ACL identity principle

An archived ACL is meaningful only together with the identity namespace to which its principals belong. Access-control entries may refer to Unix UID/GID identities, named users or groups, Windows/Active Directory SIDs, realms/domains, or storage-vendor mappings between those forms. The storage administrator controls ACL policy, inheritance and export behaviour; KU identity services and the destination storage configuration determine whether an archived principal still resolves at restore time.

BRIC therefore distinguishes preservation from replayability. The archive may preserve an ACL exactly as historical metadata while a future destination is unable to apply it, or while the destination supports the ACL model but can no longer map one or more archived principals. A fifteen-year restore must not assume the same filesystem protocol, storage vendor, Active Directory domain, UID/GID allocation or identity-mapping policy that existed when the archive was written.

6.3Role separation

Each host declares its role in /etc/bric/bric.conf. Every command asserts the role it needs and refuses to run on the wrong host: the user CLI requires BRIC_ROLE=slurm, the tape daemon requires BRIC_ROLE=tape. The updater reads the role from the configuration file and refuses a conflicting --role argument on the command line, which prevents a tape-role update from being applied to the cluster host or the reverse.

6.4User provisioning

Operational authorisation

The technical provisioning step is performed only after the institutional and management approvals defined in §6.7. KU controls institutional identity and access to research data; BRIC controls authorisation to use the archive and issuance of the archive key.

Following approval, bric-activate-user USER performs root-only, idempotent activation on the cluster host. The canonical implementation is cluster/scripts/bric-setup-user.sh. The procedure:

  1. Validates the institutional identity. The KU account must resolve through NSS/AD; UID 0 is refused and the user home must exist.
  2. Serialises provisioning with a catalogue-scoped lock so two administrators cannot create competing keys.
  3. Creates or repairs the personal key. The key is a 32-byte random secret, Base64 encoded, stored at ~/.bric/<user>_user_key.txt, mode 0600, owned by the user. If an authenticated escrow exists and the home key is missing, the same key is restored from escrow; if both exist and differ, provisioning fails rather than rotating silently.
  4. Creates and self-checks institutional escrow. The personal key is wrapped and authenticated under the institution master key and the stored escrow is immediately unwrapped and compared with the home key.
  5. Creates the managed runtime environment, private state/PID directories, the host-local allocator lock directory, central per-user logging with administrator-read ACLs and a private home-log fallback.
  6. Installs the required catalogue/runtime permissions and enables the escrow policy.
  7. Performs strict post-verification as the target user, including key format/equality, filesystem modes, logging ACLs, runtime access and a real bric status invocation.

Under the BRIC operational onboarding procedure, a copy of the personal key is also delivered directly to the authorised user on dedicated USB media and the user signs a receipt. The cluster copy remains the normal operational key; the USB copy provides independent user custody and must be protected as described in §6.7.

6.5Idempotency and fail-closed rules

Provisioning is safe to re-run and deliberately fails closed around key identity:

  • A personal key is never rotated implicitly. Existing home key and escrow must resolve to the same 32-byte secret.
  • Missing home key plus valid escrow restores the existing key; existing home key plus missing escrow escrows that same key.
  • An unmanaged or symlinked ~/.bric/env.sh is refused rather than overwritten.
  • Concurrent provisioning of the same user is serialised.
  • The institution master key never enters normal user jobs, the QNAP bus or the tape server.
  • The user’s operational key remains protected by KU host access controls, the user’s UID and mode 0600; the tape server never receives it.

6.6Deprovisioning, retention and deletion

There is no delete operation for archived data, and this is intentional: the media is append-only, and a system that could erase an archive on request would not be an archive. The practical consequences for retention policy are:

  • Crypto-erase is the software-level erasure mechanism. Rendering a user’s archives permanently unreadable requires destruction of every recoverable copy of that user key: the protected cluster/home key, the user-held USB copy, the institutional escrow and any authorised additional copy. The effect is irreversible and coarse because the same user key is reused across that owner’s projects. Whether this satisfies a particular GDPR or retention obligation is a governance/legal determination outside the code.
  • Physical destruction of both cartridges of a pair is the alternative, and removes the ciphertext itself. It affects every project stored on those cartridges, which is bounded, because a cartridge is assigned to exactly one project.
  • The audit trail is append-only by design. Both catalogues carry an audit_log table recording who did what, when, and with what result — precisely so that in ten years a question of the form "that project was never deleted" has an answer.
  • Account departure. When a researcher leaves, their archives remain readable by the institution through the escrow and the master key. No action is required to preserve access; a deliberate decision is required to remove it.

6.7User onboarding and authorisation procedure

Purpose

This procedure defines how a user is authorised to use BRIC Archive 2.0 and how the user’s personal encryption key is issued and handled. BRIC Archive does not provide an independent identity-management system and does not determine access rights to the underlying research data. Authentication and filesystem authorisation remain under KU administration.

6.7.1Prerequisite institutional identity

Before BRIC Archive access can be requested, the user must already be an authorised KU user with a valid KU identity. Creation, verification, suspension and termination of that account follow normal KU identity-management procedures. Remote access to the BRIC cluster requires the KU VPN and successful authentication to the designated gate/login host.

6.7.2Access to research data

Once authenticated, the user can access only files and directories permitted by existing filesystem permissions, Unix groups, ACLs and project controls assigned through KU. Authorisation to use the tape archive does not grant access to additional research data; BRIC runs with the user’s operating-system identity.

6.7.3Request for BRIC Archive access

The user submits a written request by e-mail to the BRIC Archive administrator and the responsible BRIC management representative. The request identifies at minimum the user’s name, KU user ID and research group or organisational unit. No archive key is issued before management approval; the approval e-mail is retained as part of the authorisation record.

6.7.4Creation of the archive user

Following approval, the administrator activates the user with the standard provisioning command. A unique personal archive key is generated or recovered consistently with the authenticated escrow and installed in the user’s protected ~/.bric directory at mode 0600. The key is associated with that individual user and is not shared between researchers or groups.

6.7.5Delivery of the encryption key

A copy of the personal key is transferred to dedicated USB media and delivered directly to the authorised user. It must not be distributed through ordinary e-mail, messaging systems or uncontrolled electronic channels.

At delivery the user signs a key-receipt document confirming receipt of the USB device, responsibility for preventing disclosure/loss/unauthorised copying, secure storage accessible only to the authorised user, and the obligation to report suspected loss, theft or compromise immediately to BRIC IT. The signed receipt is retained by BRIC.

6.7.6Use and location of the encryption key

Normal backup and restore operations use the protected key stored in the user’s KU-managed cluster home. The key file is owned by the user and readable only by that user. The USB copy should normally remain disconnected and securely stored; it is an independently held copy rather than a requirement for every archive operation.

The personal data-encryption key must never be copied to the QNAP staging bus, the tape server or the tape library. The tape server receives only already-encrypted archive objects and has no access to ISILON source data.

6.7.7User responsibility for the USB copy

The user is responsible for the physical protection of the issued USB device. It must not be shared, copied to personal cloud storage, transmitted by ordinary e-mail or provided to unauthorised personnel. Loss or suspected compromise must be reported immediately to the BRIC Archive administrator.

6.7.8Completion of a project and physical tape custody

When a project is declared complete and its archive media have passed the required verification procedures, the two copies are stored separately: one in secure custody at BRIC and one in separate secure custody at Panum. The copies must not be stored at the same physical location. Tape movement and custody are recorded by cartridge barcode.

6.7.9Delivery of an archive copy to the user

Where formally requested and authorised, one physical archive copy may be released to the user. The handover records project, cartridge barcode(s), transfer date, recipient identity and acknowledgement of receipt. The recipient then assumes responsibility for physical protection of that copy.

7Key management and cryptography

7.1Key hierarchy

Two levels of data-recovery secret exist, kept separate.

Personal user key
One per KU identity: 32 random bytes, Base64-encoded on one line. The normal operational copy is stored in ~/.bric/<user>_user_key.txt, mode 0600, owned by the user inside the KU-managed cluster environment. A separate copy is delivered to the user on dedicated USB media under the onboarding procedure. The key encrypts every chunk of that user’s archives and the encrypted project catalogue. It never reaches the QNAP bus or tape server in plaintext.
Institution master key
A 32-byte administrative recovery secret located by BRIC_MASTER_KEY_FILE, normally a root-only file on the cluster host. It wraps authenticated escrow copies of user keys and is used for authorised break-glass recovery. It never enters normal user jobs, never reaches the QNAP payload bus, never reaches the tape server and is never written to tape.

A third, non-data key pair exists for bus authentication (§7.5). It signs protocol messages; it decrypts nothing.

7.2Payload encryption

Two keys are derived from the user key with explicit domain separation:

ENC_PASS = sha256( USER_KEY + ":encryption" )
HMAC_KEY = sha256( USER_KEY + ":authentication" )

Both are used as lowercase hexadecimal strings. ENC_PASS is supplied to OpenSSL as a passphrase; HMAC_KEY is the HMAC key. Payload encryption is byte-compatible with:

openssl enc -aes-256-cbc -pbkdf2 -iter 10000 -pass file:PASSFILE

The streaming chunker implements exactly this format natively rather than shelling out, so that a multi-terabyte stream is encrypted in one pass with no plaintext ever written to disk. Concretely, for each chunk the helper generates 8 random salt bytes, writes the OpenSSL Salted__ header followed by the salt, derives 48 bytes with PBKDF2-HMAC-SHA256 over the passphrase and salt at 10 000 iterations (32-byte AES key plus 16-byte IV), and encrypts in CBC mode with PKCS#7 padding. While the ciphertext is written it simultaneously accumulates the SHA-256 of the ciphertext and the HMAC-SHA256 of the ciphertext — both computed over the complete file including the salted header.

The parameter is pinned and recorded per chunk and in the on-tape recovery kit, so if the system ever admitted human-chosen passphrases the count could be raised for new data while old tapes remain readable.

7.3Encrypt-then-MAC and verify-before-decrypt

Every path that consumes a blob — normal restore, disaster recovery, and the standalone on-tape recovery script — computes the HMAC-SHA256 of the ciphertext and compares it against the expected value from the catalogue before the blob is passed to openssl -d or to tar. A mismatch is refused, not logged and continued.

This single control does two jobs at once. It rejects tampered or forged ciphertext before any parser touches it, and it removes an entire class of path-traversal and archive-parser attacks: hostile data never reaches tar. In disaster recovery the failure is not fatal but healing: the primary copy that fails its HMAC is abandoned and the backup copy on the partner cartridge is read instead.

Independently of the MAC, the ciphertext SHA-256 is verified at three further points: immediately after every tape write (read back and re-hash), when a blob is staged back for restore (the tape daemon re-hashes before publishing it on the bus, and marks the cartridge SUSPECT on mismatch), and during scheduled re-verification of a whole cartridge.

7.4Institutional escrow

The escrow format is authenticated and versioned:

v2:<hmac_hex>:<ciphertext_b64>

ciphertext = openssl enc -aes-256-cbc -pbkdf2 -iter 10000 -a -A -salt -pass file:MASTER
hmac = HMAC-SHA256( ciphertext_b64 ) under key sha256( MASTER + ":escrow-auth" )

Unwrapping verifies the HMAC first and refuses to decrypt on mismatch, so an attacker with write access to the catalogue cannot silently corrupt a wrapped key and have the damage surface only years later at break-glass time. Legacy unauthenticated escrows are still readable for backward compatibility.

Historical note relevant to assurance

An earlier implementation produced the escrow ciphertext without base64 armour. Because shell command substitution strips NUL bytes silently, roughly a fifth of escrows were being corrupted invisibly. The current implementation uses the -a flag across all four consumers, and the escrow self-check that immediately unwraps and compares after writing exists precisely so that a defect of this shape cannot recur undetected.

At project close, the user's job copies the already wrapped escrow ciphertext to tape as user_key_escrow.v1, together with a project and owner binding:

BRIC-USER-ESCROW-V1
project=<project>
owner=<owner>
escrow_b64=<base64 of the v2 escrow string>

The close job never reads the master key. Break-glass recovery verifies the artefact's SHA-256 against the tape's table of contents, checks the project binding, verifies the escrow HMAC, unwraps with the institution master key, and then cross-checks that the owner named in the escrow matches the owner recorded in the decrypted project catalogue.

7.5Bus signing keys

Marker authentication uses ECDSA over NIST P-256 with SHA-256, via openssl dgst -sha256 -sign and -verify. The choice of primitive is a portability constraint rather than a preference: Ed25519 has no command-line signing path in OpenSSL 1.1.1, which is what the RHEL 8 gate node ships, and a keygen-only capability probe had previously reported success on a host that could not actually sign. The setup script now exercises a full sign-and-verify round trip before declaring the host capable.

Signing is symmetric in direction: each side signs what it publishes with its own private key and verifies what it consumes with the peer's public key. The tape server therefore holds a private key — but a signing key is not a data secret, so the host remains keyless with respect to data while still being able to authenticate its own receipts.

Trust-boundary note — the cluster signing key is shared with user processes

With require_bus_signing=1, bric-run and bric-setup-user.sh --strict-runtime-checks explicitly require the calling researcher to be able to read BRIC_BUS_SIGN_KEY. The current design therefore authenticates “a process possessing the cluster-side key”, not a privileged cluster service distinct from archive users. This is useful against a QNAP-only attacker or an unauthorised NFS writer who lacks the key, but it is not protection against a malicious onboarded user. A stronger boundary would move signing behind a privileged broker or use per-user signing identities with an explicit trust policy on the tape side.

7.6Parameter pinning and format versioning

Every persistent format carries a version tag so a future BRIC-FORMAT-V2 can evolve without orphaning V1 media: bus markers are BRIC-MARKER-V1, the tape index begins # BRIC tape TOC v1, the on-tape recovery kit begins BRIC-FORMAT-V1, and config.format_version='1' is recorded in both catalogues. Cryptographic parameters are recorded per chunk in the catalogue and again in the plaintext README_RECOVERY.txt on every cartridge. A version header in front of the ciphertext itself is explicitly deferred to V2 so as not to break the current read path.

7.7Cryptographic review notes

Three points a reviewer should weigh explicitly.

  • CBC without an authenticated cipher mode. The system uses AES-CBC plus a separate HMAC rather than AES-GCM. The reason is longevity: openssl enc has no AEAD mode with a stable, scriptable command-line interface, and the recovery promise requires that a person in 2040 with nothing but openssl, sha256sum and tar can open a blob. Encrypt-then-MAC over the full ciphertext, verified before decryption, is the correct composition and is applied consistently on every read path.
  • Key derivation by hashing with a suffix. sha256(key + ":encryption") is not HKDF, but the input is a full-entropy 32-byte secret and the two labels are distinct and fixed, so the derived keys are independent for practical purposes. The choice buys reproducibility by hand with coreutils, which HKDF would not.
  • Derived HMAC key on the command line. Several call sites pass the derived authentication key as an openssl dgst -hmac argument, which makes it visible in the process table to other users on the shared login node for the duration of the call. This exposes the authentication key, not the encryption key, and the two cannot be derived from one another — the impact is the ability to forge a MAC for someone whose restore is running, not the ability to decrypt. It is nonetheless a real weakness on a multi-user host and is carried as a finding in §17.3.

8The staging bus protocol

8.1Layout and marker vocabulary

The two hosts communicate exclusively through small files on the shared QNAP NFS tree. There is no socket, RPC or message queue; the tape server polls.

<bus>/archive/<project>/<run_id>/
    chunk_NNNN.enc            encrypted payload
    chunk_NNNN.enc.sha256     ciphertext digest sidecar
    chunk_NNNN.enc.hmac       ciphertext MAC sidecar
    chunk_NNNN.meta           signed chunk metadata
    chunk_NNNN.READY -> .CLAIMED -> .DONE | .ERROR
    run.RESERVE_REQUEST -> run.RESERVED | run.DENIED
    run.RESERVE_EXTEND_REQUEST -> run.RESERVE_EXTENDED | run.RESERVE_EXTEND_DENIED
    run.PROJECT_CLOSING -> run.CLOSE_PLACEMENT -> run.CLOSE_CATALOGS -> run.CLOSED
    run.ABORTED -> run.ABORT_DONE
    close/

<bus>/restore/<project>/<req_id>/
    request                      protocol=restore-progressive-v1
    request.PROGRESS             signed, refreshed heartbeat/progress
    staged_<run>__cNNNN.enc
    staged_<run>__cNNNN.READY
    staged_<run>__cNNNN.CONSUMED
    request.CANCELLED            cluster-side cancellation request
    request.STAGED               terminal tape-side result

For progressive restore the tape daemon stages one chunk, publishes its signed READY receipt and waits for the cluster’s signed CONSUMED acknowledgement before staging the next. This bounds reverse-bus occupancy to approximately one chunk per restore request. The most safety-critical archive-direction message remains DONE, because it authorises freeing the staged producer blob only after both tape copies are verified.

8.2Atomic claim

Taking work off the bus is a single rename() from chunk_NNNN.READY to chunk_NNNN.CLAIMED. Exactly one caller can win. There is no lock manager, no lease table and no coordination protocol — which is why the POSIX assumption in §4.5 is load-bearing. After winning, the daemon explicitly refreshes the marker's modification time, so the stale-claim TTL measures time since this daemon acquired the claim rather than the age of the original publication.

8.3Marker authentication

Marker signing is a cryptographic defence against forgery on the shared export, complementary to export permissions. Three properties are worth spelling out.

Detached signature published first

The signature is written to a sidecar <marker>.sig and published before the marker itself, so a consumer can never observe a signable marker without its signature.

Domain separation and path binding

What is signed is not the bare marker body but a canonical envelope:

BRIC-MARKER-V1\n<project>/<run_id>/<marker_name>\n<body>

The verifier rebuilds that prefix from the file's real location on disk. A valid signature therefore cannot be moved onto a different marker name, a different run, or a different project — not even when the bodies are byte-identical, because the reconstructed prefix differs and the signature fails cryptographically. On top of that, consumers check semantic binding: run_id must equal the directory name, chunk_no must equal the number in the file name, project must equal the parent directory.

Mandatory mode

Backward compatibility — "sign if the keys are present" — is convenient during commissioning and dangerous in production, because a deployment that forgets an environment variable would silently degrade to an unsigned bus. Setting the catalogue key require_bus_signing=1 on both sides removes that failure mode: the tape daemon refuses to start and the cluster scripts refuse to publish if the signing or verification key is missing.

Deployment check — signing enforcement is conditional at install time

The shipped role configuration files set BRIC_REQUIRE_SIGNING=1, and the setup script defaults to the same. However, the setup script writes require_bus_signing=1 into the catalogue only if the corresponding key files already exist on that host at setup time; otherwise it writes 0 and prints a warning telling the operator to enable it after distributing the keys. The database default in the shipped schema is also 0. Enforcement must therefore be verified after deployment rather than assumed:

sqlite3 $BRIC_DB "SELECT value FROM config WHERE key='require_bus_signing';"
sqlite3 $BRIC_TAPE_DB "SELECT value FROM config WHERE key='require_bus_signing';"

Both must return 1 in production. This is listed as a required acceptance check in §17.3.

8.4Export permissions — a security control, not an option

The bus may be readable by authorised hosts because payloads are ciphertext, but write access must be limited to principals that are intentionally allowed to participate in the archive protocol. In the current local-mode implementation that set necessarily includes the onboarded researcher's process: preflight and activation explicitly test that the user can write BRIC_QNAP, and the user process publishes reservation, chunk and close markers itself. The older wording “service accounts only” is therefore too narrow. NFS host allow-lists, coherent mapping/squash and restrictive setgid/ACL policy remain essential to exclude arbitrary campus/NFS clients, but they do not isolate one onboarded archive user from another. Marker signing adds protection against writers without the relevant private key; under the current shared cluster-signing-key model it is not a per-user authorisation control.

8.5Bus lifetime and cleanup

The bus is transport, not storage. Individual blobs are freed as soon as both tape copies are verified — not at the end of the run — which bounds peak staging occupancy to roughly the sliding-window size. Whole run directories are removed only after the cluster catalogue records a terminal state and the corresponding signed receipt has been verified: run.CLOSED for a successful run, run.DENIED for a refused one, and run.ABORT_DONE for a failed or cancelled one. Cleanup is path-bound (the run identifier must be prefixed by the project name, and the resolved path must match the expected bus location exactly) so a malformed name cannot cause a deletion elsewhere. Operators can inspect and remove leftovers from older releases with bric-bus-cleanup --dry-run followed by bric-bus-cleanup. Setting BRIC_KEEP_TERMINAL_BUS=1 retains terminal directories for forensic work.

9Backup: end-to-end walkthrough

This section follows a single command from the shell prompt to a sealed pair of cartridges. The deployment currently runs in BRIC_RUN_MODE=local, in which the whole pipeline executes on the gate host; §9.10 covers the Slurm-distributed mode.

9.1Command entry, validation and preflight

The user runs:

bric backup mouse_rnaseq /mnt/isilon/projects/mouse_rnaseq

The installed bric command is the operational wrapper. In order it: answers version and every form of help before loading any runtime, running preflight or creating a job record; normalises the friendly positional form into the explicit long form; then fully validates the operand set, so that a typo or a missing operand can never leave a stray backup.unknown job record behind.

Only then does it load the user's ~/.bric/env.sh, resolve an OpenSSL runtime (keeping the current binary when it is already version 3 or newer, otherwise initialising Environment Modules and selecting the newest module this UID can actually load — the configured module name is a preference, not a requirement), and run preflight:

  1. Runtime availability: OpenSSL for local mode, or sbatch and the executable job scripts for Slurm mode.
  2. Bus mount: the exact declared mount point must be a mount point, and with BRIC_REQUIRE_NFS_BUS=1 its type must be NFS; the bus root must exist under it and be writable by the caller.
  3. Personal key: present, non-empty and readable. If not, the message names the exact administrative command needed.
  4. If require_bus_signing=1: this user must be able to read both the cluster signing key and the tape public key.
  5. Source integrity: the scan described next.

Any failure prints a numbered [FAIL] line and stops. --skip-preflight exists and is documented as discouraged.

Once preflight passes, a local-mode backup detaches by default. The wrapper starts a supervisor in its own session and process group, records a job identifier, PID, action, project, start time and log path under ~/.bric/pids, redirects all output to a private log under ~/.bric/log/jobs, and prints the job id together with the exact commands to follow or cancel it. The researcher can close the SSH session; the archive continues. --wait keeps the historical foreground behaviour.

9.2Source-integrity gate — before any tape is committed

This gate runs as the calling UID before any tape reservation, so append-only media are not consumed only to discover late that part of the requested tree was unreadable.

  • Every explicit --exclude RELPATH is an exact, validated relative subtree and is recorded as a user-declared exclusion.
  • Directories must be readable/traversable and regular files readable; symbolic links are archived as links.
  • Without --force, every precisely identified unreadable/untraversable path is reported and the run stops before reservation.
  • With --force, only the precisely identified unreadable paths are omitted and recorded with reason force-unreadable; source sizing/reservation are recomputed over the remaining readable scope. Unclassified traversal or I/O failures remain fatal. --force is therefore not equivalent to skipping preflight.
  • A separate scan records regular-file count, logical bytes and allocated bytes for progress/capacity context. GNU tar remains authoritative for the archived bytes.

Exclusions, forced omissions and scan denominators are stored in the catalogue and copied into the encrypted project catalogue so future recovery can distinguish intentional scope decisions from missing data.

9.3Run creation and tape reservation

The planner creates the run and its scope record in one transaction, so a run cannot exist with an ambiguous scope. The insert is conditional:

INSERT INTO runs (...) SELECT ...
WHERE NOT EXISTS (SELECT 1 FROM runs
 WHERE project_name = ?
 AND status IN ('PLANNING','RESERVED','PRODUCING','DRAINING','CLOSING'));

If the insert affects no rows, another run is already active for that project and the command stops (invariant I2). Run identifiers are <project>__<UTC timestamp>__<counter>, with the counter incremented inside an explicit immediate transaction so two runs starting in the same second cannot collide. The identifier's lexicographic order is therefore also its chronological order, which disaster recovery later relies on to decide which run wins when a path exists in several.

Policy checks at this point: the project must belong to the requesting owner; if require_user_escrow=1, the owner must have an escrow row; if require_bus_signing=1, signing keys must be configured.

The planner then requests capacity. Because a streaming producer does not know its final size in advance, it asks for an initial allocation of roughly one chunk plus ten per cent, publishes a signed run.RESERVE_REQUEST, and waits for run.RESERVED or run.DENIED. The response's signature is verified and its run_id must bind to this run. A denial is recorded with its reason, audited, notified, cleaned up from the bus and reported to the user. A grant records the number of pairs and the granted logical capacity in bytes.

Semantics B — media before bytes

No byte of ciphertext is produced before tape has been reserved. Reservations are computed on the ciphertext size, adding tar framing overhead and a configurable margin (reservation_overhead_pct, default 2%), so a project with very many small files is not under-reserved. Reservations carry a TTL (192 hours) and a heartbeat, so a dead run releases its media automatically.

9.4Parallel tar-stream producer

Local mode is still one user-visible backup and one run_id, but the source producer is parallel by default. After preflight and reservation it builds a cluster-local, NUL-safe manifest of the included scope, assigns each regular file to exactly one worker using logical-byte balancing, and launches up to four independent GNU-tar → bric-tar-stream pipelines concurrently.

All workers publish into one global contiguous chunk namespace. A host-local allocator lock plus a SQLite BEGIN IMMEDIATE transaction reserve the next chunk number and account for already published and currently allocated worker chunks before production proceeds. Directory and symlink metadata are emitted once after all regular-file workers, keeping restrictive directory metadata globally last.

The default target is 128,000,000,000 bytes (128 GB decimal) per worker chunk. GNU tar uses a 4 MiB outer record (tar_blocking_factor=8192) to reduce pipe/syscall overhead. The tar-aware Go helper still computes each regular file’s plaintext SHA-256 while consuming the actual source stream; no content-hash pre-pass is introduced.

  • Name safety. Absolute names, .. components and embedded NULs are rejected.
  • Chunking. Normal members accumulate into independent TAR_PART archives; an oversized regular file is split into ordered LARGE_FILE_CHUNK byte ranges.
  • Encryption. Each chunk is encrypted in streaming OpenSSL-compatible AES-256-CBC form while ciphertext SHA-256 and HMAC-SHA256 are accumulated.
  • Capacity. Workers cannot allocate another chunk without passing the shared stream gate; reservation extension remains signed and pair-based.

Sparse files

Sparse handling uses GNU PAX 0.1 sparse-map records from the authoritative tar stream rather than filesystem block accounting. Materially sparse members may be batched into a valid multi-member sparse TAR_PART (default mapped-data target 4 GiB). Byte content is authoritative; allocation topology is not guaranteed, so zero ranges may restore as holes even when the source had physically allocated zero blocks.

9.6Publication of a chunk

Before a parallel worker opens a new chunk, bric-stream-allocate.sh obtains the per-run host-local allocator lock, evaluates reservation headroom and atomically reserves MAX(chunk_no)+1 in the catalogue as ALLOCATED. When ciphertext is complete, publication:

  1. atomically converts the placeholder to the completed chunk row and commits the file rows;
  2. writes the ciphertext SHA-256 and HMAC sidecars;
  3. publishes the signed chunk metadata marker;
  4. publishes the signed READY marker;
  5. derives run chunk/byte totals from authoritative catalogue rows and emits structured progress.

The tape daemon can therefore observe READY only after the chunk is complete, catalogued and hashed. Concurrent workers never create synthetic sub-runs or overlapping chunk numbers.

9.8Drain and finalisation

When the stream ends, the run moves to DRAINING and the finaliser waits for every chunk's receipt. Its behaviour on each pass:

  • Up-front reconciliation. Any chunk still in PLANNED, PENDING, PRODUCING or ERROR at this point means a producer died without leaving a marker. That is detected immediately rather than after the drain timeout.
  • Receipt verification. For each DONE marker the signature is verified and the run_id binding checked before the staged blob is freed. This is the single most important verification in the system: a forged DONE would delete data that never reached tape.
  • Error propagation. A verified ERROR marker fails the run with the tape server's own reason.
  • Heartbeat. The reservation heartbeat is refreshed on every pass so a long, healthy drain does not expire its own media reservation.
  • Failure path. On any failure the run is marked FAILED, a signed run.ABORTED is published, and the finaliser waits for the tape server's run.ABORT_DONE before cleaning the bus. If the acknowledgement does not arrive, the bus directory is deliberately preserved for daemon recovery.

When all chunks are verified on both cartridges, the run moves to CLOSING, the private run-state scratch is removed, and a signed run.PROJECT_CLOSING is published.

9.9Close: what is actually written to the cartridges

Closing is a four-message handshake and is the part of the protocol most hardened against partial completion.

  1. The daemon answers PROJECT_CLOSING with a signed run.CLOSE_PLACEMENT listing, for every chunk, the volume tag and file number of both copies, plus the project's cartridges.
  2. The cluster records the cartridges in project_tapes and builds the close artefacts on local storage, never on the shared bus:
    • catalog_project.enc — a SQL dump of everything about this project (projects, runs, chunks, files, exclusions, source scan, source semantics, source changes, project tapes) plus an embedded placement table mapping chunk to cartridge and file number, encrypted with the owner's key.
    • user_key_escrow.v1 — the already master-wrapped, authenticated escrow ciphertext, bound to project and owner. The close job never reads the master key.
    • schema.sql, README_RECOVERY.txt, restore_from_tape.sh — plaintext, non-secret, self-contained recovery kit.
    The plaintext catalogue dump is created in local scratch and deleted immediately after encryption; the passphrase file is mode 0600 and removed on every exit path.
  3. The cluster publishes a signed run.CLOSE_CATALOGS carrying a manifest of exactly those artefacts as artifact|name|kind|sha256 lines.
  4. The daemon verifies the manifest signature and bindings, then enforces it: every listed artefact must be present on the bus, must match its declared SHA-256, and must be appended and read-back-verified on every cartridge of the project. Only then are the tables of contents written — last — and only when every artefact is VERIFIED on every cartridge, and both drives are confirmed empty with the media back in their slots, is run.CLOSED published.

Two refusal rules are absolute. A missing or mismatched artefact blocks sealing; the run stays unsealed and is retried on the next pass. An artefact already VERIFIED under the same identity but with different content is a fatal error, never a silent skip.

The cluster verifies the run.CLOSED signature and binding before recording the run as closed, notifying the owner, writing the audit entry and cleaning the bus.

9.10Slurm mode

The distributed mode is retained and will be used once the compute nodes have the Isilon and QNAP mounts. Its differences are operational rather than architectural:

  • bric backup does not plan on the login node. It submits a short orchestrator job that plans, waits for the reservation, submits the chunk array and the dependent finalise job, and exits — so an SSH drop cannot kill the pipeline. The export to jobs is an explicit whitelist of BRIC_* variables, never --export=ALL.
  • The finalise job depends afterany, not afterok, so it runs even when array tasks fail; it is the single reconciliation handler.
  • --requeue is safe because everything is idempotent: a re-executed task whose chunk is already complete exits zero without re-staging, and the tape server re-publishes DONE from the verified catalogue rows rather than writing a duplicate segment.
  • The archive partition is sized as I/O-bound work (2 CPUs, 2 GB, constrained to nodes with the mounts) and is configured as a good neighbour: low queue priority, no pre-emption of running jobs.
  • Slurm mode retains the serial/per-file planner rather than the local parallel tar-stream producer. It records current large-file mode/metadata fields and applies the same regular-file special-bit policy. --exclude and --source-change-policy record remain local-producer-only and are refused in Slurm mode rather than silently ignored.

9.11Fidelity and metadata limits

Archive-time preservation and restore-time replay are deliberately treated as different questions. BRIC records the byte content and the selected metadata that the source exposes at archive time; whether every recorded metadata item can later be reproduced depends on the capabilities and identity environment of the restore destination.

Captured / preserved by the archiveRestore-time limits
  • Regular-file contents, byte-exact, with plaintext SHA-256 per file
  • Directories, including empty directories
  • Modification times
  • Ordinary regular-file permission bits (0777)
  • Directory mode semantics, including sticky directories
  • Symbolic links, archived as links
  • File names containing spaces/newlines and other hostile bytes supported by the catalogue path handling
  • Selected ACL/xattr metadata for current archives where it is exposed by the source: user.*, POSIX ACL representation and system.nfs4_acl
  • Sparse byte content; materially sparse files remain tape-efficient
  • Destination capability is authoritative. A future filesystem may not support, expose or permit writes for the same ACL/xattr model that existed at archive time.
  • Identity mapping can change independently of filesystem support. An ACL may be representable but contain principals whose UID/GID, SID, group, realm or directory-service mapping no longer exists.
  • UID/GID ownership is not replayed by BRIC — restore uses --no-same-owner; objects are owned by the restoring identity.
  • Setuid, setgid and sticky bits on regular files are deliberately cleared because ownership is not restored; directory sticky semantics are retained where applicable.
  • SELinux/security/trusted and unrelated system xattrs are outside the archival contract.
  • Hard-link identity is not preserved; hard links restore as independent regular files.
  • FIFOs, sockets and device nodes are not treated as archive data.
  • Allocation topology is not guaranteed; byte content is authoritative.
Protocol- and vendor-neutral rule

BRIC does not define metadata fidelity by filesystem name or protocol version. NFSv3, NFSv4, a future NFS generation, SMB, a local filesystem or a future storage platform may expose different capabilities under different administrative policies. Restore decisions must therefore be based on what the destination can actually represent and apply, not on a hard-coded assumption such as “NFSv4 supports ACLs”.

For TAR_PART objects current archives can carry ACL/xattr records inside the tar stream. For LARGE_FILE_CHUNK, ordinary mode plus a versioned Base64 metadata envelope are stored in the encrypted project catalogue. Archives created before those metadata fields existed cannot reconstruct metadata that was never recorded; their already-catalogued mtime remains recoverable. Preservation of a metadata record on tape is not, by itself, a guarantee that a future destination can replay it.

Why ST driver options are checked

Two Linux SCSI tape driver options would silently break BRIC's physical file-number invariant: MT_ST_TWO_FM (0x10) makes a close write two filemarks, and MT_ST_FAST_MTEOM (0x20) positions to end-of-data by a route after which the kernel documents the file number as invalid. The append path asserts a contiguous single-filemark file mode before writing.

10.2Inventory, pairing and roles

Cartridges are registered from the physical library with bric-tape-import-inventory --dry-run followed by --apply, which reads mtx status, backs up the catalogue before the transaction, never reinterprets a cartridge that is already written or project-assigned, and reports and skips incomplete pairs.

Pairing follows barcode parity: by default even barcodes are PRIMARY/on-site and odd are BACKUP/off-site, with the BACKUP of a pair always PRIMARY+1. The parity convention is configurable and is used only for initial assignment, pairing derivation and rebuild fallback — the authoritative role at runtime is the tapes.role column, not the label digits. A cartridge is assigned to exactly one project (tape_exclusivity=project); the other two values in the schema are reserved for future work and the daemon refuses to start on them rather than silently treating them as project.

10.3Capacity model and project-scoped reservations

Usable capacity per cartridge is capacity_tb − headroom_tb. With an 18.0 TB cartridge, 0.30 TB headroom and the current 128 GB decimal target, approximately 138 target-sized chunks fit before the reserved headroom. A chunk never spans tape pairs, so reducing the target from the former near-terabyte scale also reduces worst-case packing tail and bounds random-restore read amplification.

A reservation is project-scoped. It considers only complete healthy pairs already assigned to the project plus the minimum complete unassigned healthy pairs needed to cover requested bytes. Selected media transition atomically to RESERVED and are bound to project/owner. If capacity remains short, only pairs newly selected by that request are rolled back; existing project media stay assigned. Denials are signed and include the concrete reason/shortfall.

10.4Write path and verification

For each physical copy of each chunk the daemon:

  1. Records intent before tape I/O in a segments row with state WRITING.
  2. Positions to end-of-data and validates the physical file counter.
  3. Streams the QNAP blob to the non-rewinding tape device. QNAP input uses a larger application read block (default 4 MiB) while physical tape records remain 262144 bytes.
  4. Relies on the driver’s single flushing filemark and verifies that the physical file number advances by exactly one.
  5. Marks the segment WRITTEN and records its physical file number.
  6. Verifies by streaming the just-written tape file through simultaneous byte counting and SHA-256 calculation. No segment-sized read-back tempfile is materialised on local disk.
  7. On exact size and hash match, atomically marks the segment VERIFIED and accounts consumed capacity.
  8. On a clean short stream or exact-size hash corruption, abandons the physical append, accounts its consumed capacity and penalises media health (SUSPECT for immediate write verification; periodic verification can mark media BAD). A transport/local verification failure is kept distinct so a local host failure is not automatically blamed on the cartridge.

A chunk DONE receipt is published only after both physical copies are VERIFIED. Existing verified copies are reused idempotently after retries; if only one partner copy survives, only the missing partner is rewritten when its payload identity still matches.

10.5Positioning and filemark semantics

Arbitrary reads — restore, periodic re-verification, TOC sniffing and disaster-recovery scans — use absolute positioning (rewind + fsf) because the requested tape file may be anywhere.

Immediate post-write verification has more context and uses an adaptive choice between:

  • relative positioning from end-of-data (eod + bsfm 2), with file-number post-conditions; and
  • absolute rewind + fsf.

The choice uses configured/measured rewind, forward-filemark and reverse-media costs. Any failed command or landing-position mismatch causes a safe absolute fallback. The selected method, estimates, landing checks and fallback reason are logged. The physical tape block size remains unchanged.

10.6Concurrency, locking and the singleton

Three locking layers coexist:

Daemon singleton
An absolute-path singleton lock (canonically /var/lock/bric_tape.lock) is acquired non-blocking. The daemon also acquires every historically deployed lock namespace so an older daemon blocks a new generation and vice versa. Relative/symlinked or otherwise unsafe lock paths are rejected fail-closed.
Generation work fence
A second lock, inherited by every worker and every external command the daemon launches, and acquired blocking at startup. If a daemon is killed with SIGKILL, a surviving dd, mt or command substitution still holds the fence; the new daemon may take the singleton immediately but cannot begin recovery or reclaim until every known generation fence is clear. Workers close the singleton descriptors immediately and keep only the fence, which is exactly the asymmetry the property requires.
Changer and per-drive locks
The changer lock is held only while inventory is inspected or media is moved. Once cartridges are loaded, each drive has its own lock, so the two drives stream PRIMARY and BACKUP concurrently without any command touching the same device. Media are normalised onto two distinct drives — resolving a swapped or preloaded pair — before the parallel workers are forked, with both drive locks and the changer lock held in a fixed order.

Parallel copies are asynchronous and independently timed: each drive has its own readiness, I/O and unload timing and may finish much earlier than the other. There is no lockstep requirement and no timeout keyed to whichever drive finishes first. What there is is a barrier: DONE and CLOSED cannot be published until append, filemark, read-back and hash have completed on both sides and the cartridges are back in their slots.

Even the idle sleep is guarded — it runs in a subshell that first closes both the singleton and the fence descriptors, so a daemon killed while sleeping does not leave a lock held by a sleeping process.

10.7On-tape layout and the table of contents

A cartridge is a sequence of numbered tape files. Chunk payloads are appended as they arrive; at each project close, the recovery artefacts are appended and then a plaintext table of contents is appended last:

# BRIC tape TOC v1
volumetag=<barcode>
run_id=<run>
project=<project>
file|kind|run_id|chunk_no|copy_role|filename|sha256
7|CHUNK|proj__20260904T101500Z__0012|3|PRIMARY||<sha256>
8|ARTIFACT|proj__20260904T101500Z__0012|||catalog_project.enc|<sha256>
...

The index is never rewritten. Each close appends a new cumulative TOC built only from VERIFIED rows, so abandoned partial writes are never referenced even though their blocks physically remain on the append-only medium. In disaster recovery the latest valid TOC found by scanning backwards from end-of-data wins.

The TOC deliberately contains only safe values — integers, hexadecimal hashes, charset-validated run identifiers and fixed artefact names. No user path ever appears in it; paths live encrypted inside catalog_project.enc. A guard enforces this: the number of data lines must equal the number of verified records, so if any field ever contained a newline the close fails loudly instead of writing an index that the pattern-based recovery parser could misread.

10.8Media health and re-verification

The tapes table carries wear and health telemetry: write count, mount count, write errors, read errors, last verification timestamp and a health state of OK, SUSPECT or BAD. A failed write verification marks the cartridge SUSPECT; a failed read during restore staging does the same. Cartridges marked BAD are excluded from new reservations and from pair capacity.

Scheduled re-verification is the control that catches slow LTO degradation before the data is needed:

bric-tape-daemon --verify VOLUMETAG

It re-reads every verified segment and artefact on the cartridge, re-computes the ciphertext SHA-256, updates last_verify, the read-error counter and the health state, and writes an audit entry. The intended operational pattern is one cartridge per night from cron. This is a recommended standing operational control, not an optional extra: it is the only mechanism that detects bit-rot on media that has not been read for years.

11Restore

A normal restore uses the cluster catalogue and the reverse bus. Single-file restore can address the stable logical namespace:

bric restore PROJECT DEST
bric restore PROJECT DEST --file LOGICAL_ROOT/path/to/file
bric restore PROJECT DEST --run RUN_ID --file path/to/file
bric restore PROJECT DEST --require-destination-verify
bric restore PROJECT DEST --allow-metadata-degradation --require-destination-verify

11.1Data integrity and metadata fidelity

BRIC treats restore correctness as two independent results:

Result dimensionQuestion answeredAuthoritative evidence
Data integrityWere the archived file contents recovered without loss or corruption?Ciphertext HMAC before decryption, successful extraction/assembly, and plaintext destination checksum verification. A restore with checksum mismatches or missing objects is a failure, never a degraded success.
Metadata fidelityWere the archived modes, timestamps, ACLs and selected extended attributes reproduced with the same semantics?Per-metadata application results, destination capabilities and identity resolution. This result may be DEGRADED even when every file byte is verified.
The essential distinction

Metadata degraded does not mean data degraded. A restore may recover and independently verify every file while the destination refuses one or more historical ACL/xattr operations. Conversely, a metadata warning can never excuse a missing file, a checksum mismatch, a failed HMAC, a decryption error or a payload extraction error.

11.2Destination capabilities and identity namespaces

The restore destination is not assumed to resemble the source. This is essential to the fifteen-year recovery promise: filesystem protocols, storage vendors, directory services and administrative policies may all change during the lifetime of an archive.

Four layers are considered separately:

Archived metadata
What BRIC captured from the source at archive time: mode, mtime and selected ACL/xattr representations where available.
Destination capabilities
What the restore target can actually represent and write. Capability is determined by behaviour, not by the advertised filesystem name or NFS protocol version.
Identity resolution
Whether principals referenced by an archived ACL still resolve in the current environment. ACL semantics can depend on UID/GID, named Unix users/groups, Active Directory SIDs, domains/realms and storage-specific mappings between them.
Destination policy and inheritance
The storage administrator may define ACL inheritance, identity mapping, access-zone/export policy and which metadata operations clients are permitted to perform. A user can therefore be able to create and modify file contents while being unable to replace the file's security ACL.

For documentation and operational review, metadata outcomes are classified as follows:

StatusMeaning
RESTOREDThe destination accepted the metadata and its referenced principals are usable in the current identity environment.
UNSUPPORTEDThe destination cannot represent or does not permit the required metadata operation through the available interface.
UNMAPPABLEThe metadata model is supported, but one or more archived identities/principals cannot be resolved or mapped meaningfully in the current identity environment.
SKIPPED-DEGRADEDThe operator explicitly accepted metadata loss for this restore; data verification remains mandatory.

The current recovery candidate also ships bric-restore-capability-probe.sh as an operator tool. It safely tests a destination's effective create/write/unlink behaviour and its available POSIX ACL, NFSv4 ACL and xattr interfaces using a temporary probe directory. The normal bric restore path does not yet automatically run that probe; capability evidence is therefore an operational preflight when metadata fidelity is uncertain.

11.3Degraded restore semantics

Strict restore remains the default. The explicit --allow-metadata-degradation mode exists for recovery onto a destination that can safely receive and verify the data but cannot reproduce all archived ACL/xattr metadata. In the current implementation it is intentionally restricted to a fresh, empty destination, checked before the tape request is published, so degraded metadata handling cannot silently mutate pre-existing content.

The payload path remains fail-closed. Ciphertext authentication, decryption, tar/large-file extraction, file presence/type and requested destination verification remain fatal requirements. Metadata degradation is never used to convert a payload error into success.

When degradation is explicitly allowed, supported metadata is still restored where possible; unsupported/rejected selected metadata can be skipped and reported without preventing later metadata such as mtime from being attempted. The overall restore is then recorded as result=DEGRADED and metadata_fidelity=DEGRADED.

Restoring into an existing managed hierarchy

If the original directory hierarchy still exists and retains a valid current ACL policy, newly restored files may inherit that policy and therefore be fully usable by the intended current users even though BRIC cannot prove that each historical ACL was replayed byte-for-byte. This can be the correct operational result, especially on centrally managed storage. It must still be reported as metadata-degraded unless BRIC can demonstrate equivalence to the archived access-control metadata.

The restore sequence remains:

  1. Resolve the archive view. Full restore uses the latest CLOSED run. Automatic single-file restore resolves the newest closed run containing the requested LOGICAL_ROOT/RELATIVE_PATH; an explicit --run selects an exact historical run.
  2. Validate destination paths. Absolute paths, .. traversal, wrong logical roots and symlink escapes outside the canonical destination are refused.
  3. Open a restore metadata transaction. A per-UID SQLite journal on a host-local filesystem records directory metadata. Existing ancestors are snapshotted and restrictive directories are temporarily relaxed so later chunks and verification can traverse the tree. A live journal blocks a second restore to the same destination; stale journals are recovered before new work.
  4. Request progressive staging. The signed request advertises restore-progressive-v1. The tape daemon verifies it, chooses a verified physical copy (PRIMARY first, BACKUP on failure), and emits signed request.PROGRESS while positioning and reading.
  5. Read and verify ciphertext in one pass. The tape stream is simultaneously written to the staged .enc.part object and SHA-256 hashed; there is no second full QNAP read merely to compute the ciphertext digest. A bad primary copy marks that media appropriately and the backup copy is tried.
  6. Authenticate before decrypting. After signed READY, the cluster verifies the staged ciphertext HMAC before passing anything to OpenSSL or tar. Only after successful decrypt/extract or large-file append does it publish signed CONSUMED, allowing the daemon to stage the next chunk.
  7. Handle timeout/cancellation by progress, not total elapsed time. The default queue allowance is 24 hours; once signed progress has started, the default inactivity limit is 30 minutes. On a normal cluster-side failure/timeout the client publishes signed request.CANCELLED. The tape daemon finishes the current tape-file read, discards staged ciphertext, releases media and does not start another chunk.
  8. Synchronise and verify the destination. After payload placement BRIC runs sync -f DEST where supported, then verifies regular files while directories remain traversable. Results distinguish VERIFIED-DESTINATION, VERIFIED-STREAM, CHECKSUM-MISMATCH and MISSING/WRONG-TYPE. --require-destination-verify makes any stream-only result a restore failure.
  9. Finalize metadata. Directory metadata is replayed deepest-first only after payload verification. In strict mode unsupported metadata remains a failure. In explicitly degraded mode only the approved metadata-error classes are downgraded; unrelated storage/path errors remain fatal.
  10. Clean up and audit. Staged ciphertext, passphrase files and local scratch are removed, the journal is finalized, and the result is logged, audited and notified. A degraded success is persisted as such rather than being collapsed into ordinary success.
Meaning of VERIFIED-STREAM

VERIFIED-STREAM means authenticated/decrypted extraction completed without reported error but BRIC could not independently re-read and hash the final destination object. It is not a claim that the bytes were physically persisted by remote storage. Use --require-destination-verify when that stronger post-condition is required.

11.4User-visible result and communication

A degraded restore must never be communicated merely as “partial success” or “restore degraded”, because that wording can be mistaken for corrupted file content. The user-visible message must state the two dimensions separately and explain the practical permission consequence.

DATA INTEGRITY: VERIFIED
All requested file contents were restored and verified successfully.

METADATA FIDELITY: DEGRADED
The destination could not reproduce all archived access-control metadata.

Possible affected metadata:
- ACLs
- extended attributes
- identity/principal mappings

The restored files may therefore inherit the current access policy of the
destination storage system instead of reproducing the historical permissions
exactly. This does not indicate corruption or loss of the file contents.

Where known, the operator-facing record should additionally identify each relevant metadata class as RESTORED, UNSUPPORTED, UNMAPPABLE or SKIPPED-DEGRADED. The current recovery-candidate audit record persists the aggregate metadata_fidelity=DEGRADED; per-class persistence is a desirable extension because it makes a fifteen-year-old restore report self-explanatory without reconstructing old logs.

Catalogue-only queries require no tape. By default bric contents and bric find build a logical union of closed runs using LOGICAL_ROOT/rel_path, newest closed version winning for duplicate keys while older-only files remain visible. --history exposes all versions and --run RUN_ID selects one exact closed run.

12Disaster recovery

This is the section that distinguishes an archive from a backup, and it is exercised by an automated test that destroys both catalogues, the QNAP bus and every key except the user's own, then rebuilds everything from the cartridges.

12.1Owner recovery from tapes and key

bric-dr-from-tapes.sh --project mouse_rnaseq \
 --user-key-file ~/.bric/my_user_key.txt --dest /restore \
 [--file raw/sample01.bam] [--tapelib DIR]

No cluster, no catalogue, no daemon, no QNAP. The same tape abstraction is used, so the tool runs identically against real LTO hardware and against a directory of tape images. The algorithm:

  1. Find the index. For each cartridge, scan backwards from end-of-data all the way to file 1 looking for the TOC magic line. There is no fixed window: a later run appends chunks to both cartridges of a pair before its own close, so if disaster struck mid-run, dozens of chunk blobs may follow the last valid TOC. A fixed window would silently make whole cartridges — and therefore whole projects — invisible to recovery.
  2. Sniff, do not read. Each candidate is recognised by reading one 256 KiB block, not the whole file. A non-TOC candidate is a 128 GB blob; reading it per probe would turn a real-hardware recovery into days of work. Only the file recognised as a TOC is read in full.
  3. Build the map. From all matching TOCs, build chunk-to-(cartridge, file number) for both copies, and locate catalog_project.enc, user_key_escrow.v1 and, on legacy media, catalog_system.enc.
  4. Integrity before decryption, for catalogues too. The catalogue artefact's SHA-256 is checked against the value in the plaintext TOC before it is decrypted; a mismatch reports media corruption and points at the other cartridge of the pair.
  5. Open the catalogue with the two keys derived from the user key, and load the SQL dump into a temporary SQLite database. The user key is unset from the environment immediately after deriving the working keys.
  6. Rebuild the data. Runs are processed in run-identifier order — which is chronological — so when the same path exists in several runs the latest deterministically wins. Within a run, chunks are processed in chunk order, interleaving TAR_PART and LARGE_FILE_CHUNK exactly as normal restore does, so the trailing metadata chunk carrying possibly restrictive directory modes is extracted last.
  7. Verify and self-heal. Each blob is authenticated with its HMAC before decryption; on failure the tool automatically falls back to the other copy of the pair. Every restored file is re-hashed against the catalogue's plaintext checksum, and the tool exits non-zero if any verification failed.

Path safety survives this route as well: catalogue reads use SQLite's ASCII mode with unit and record separators, so a file name containing a newline arrives intact at the final comparison, and the TOC parser recognises data lines by pattern rather than by line number.

Recovery independence extends to observability: the DR script loads the standalone logging library if it is present and degrades to a no-op if it is not, so a bare recovery host without the full tree still works. This addresses a previously observed failure in which the DR script called a logging function without sourcing its library.

Disaster recovery uses the same destination metadata transaction and the same separation between data integrity and metadata fidelity as normal restore, including per-UID journalling, restrictive-directory relaxation, final deepest-first metadata replay and the optional --require-destination-verify policy. The current recovery path also accepts explicit --allow-metadata-degradation for a fresh/empty destination when ACL/xattr replay is impossible but payload recovery and verification remain possible. For archives created with the current metadata fields, large-file ordinary mode and selected ACL/xattrs are attempted after payload verification; legacy archives recover only metadata that was originally recorded. A DR result must not claim full metadata fidelity when the recovery host or destination cannot represent the historical ACL model or resolve its principals.

12.2Administrator break-glass

bric-dr-from-tapes.sh --project mouse_rnaseq \
 --master-key-file /secure/master.key --dest /restore/mouse_rnaseq

Used when a researcher has lost their key or has left the institution. The tool reads user_key_escrow.v1 from tape, verifies its SHA-256 against the TOC, checks the BRIC-USER-ESCROW-V1 header, checks that the project field binds to the requested project, decodes and verifies the escrow HMAC under the master-derived authentication key, unwraps the user key with the institution master key, and then cross-checks that the owner named in the escrow matches the owner recorded inside the decrypted project catalogue. Any of those checks failing aborts. From that point recovery proceeds exactly as the owner path. Legacy cartridges carrying catalog_system.enc are still supported through an equivalent route.

This is a privileged, auditable action: it requires administrative access to the institution master key. If the operational custody procedure keeps the recovery copy offline, it also requires obtaining that protected copy through the defined break-glass process. The code itself does not enforce offline custody.

12.3Tape-catalogue rebuild

bric-tape-rebuild-catalog.sh --out /path/new_tape_catalog.db \
 --tapelib /path/to/tapes --verify

If the tape server's SQLite catalogue is lost but the cartridges survive, this reads the most recent TOC from each cartridge and rewrites tapes, segments and tape_artifacts. --verify re-reads every file and re-checks hashes and sizes. An automated test asserts that the rebuilt catalogue is equivalent to the original. Two caveats are documented: segments.owner remains empty, because owner lives encrypted in the project catalogue; and PRIMARY/BACKUP pairing is re-derived from barcode numbering and must be revalidated against the physical inventory (mtx status) before writing resumes.

12.4Manual recovery without any BRIC software

Every cartridge carries README_RECOVERY.txt in plaintext, stating the pinned parameters and the exact commands. The complete recipe, using only openssl, sha256sum and tar:

ENC_PASS=$(printf '%s:encryption' "$USER_KEY" | sha256sum | awk '{print $1}')
HMAC_KEY=$(printf '%s:authentication' "$USER_KEY" | sha256sum | awk '{print $1}')

# authenticate BEFORE decrypting (expected value: chunks.payload_hmac in the catalogue)

 -in catalog_project.enc -out catalog_project.sql
openssl enc -d -aes-256-cbc -pbkdf2 -iter 10000 -pass file:pass.txt \

A scripted version, restore_from_tape.sh, is also written to every cartridge; it verifies the HMAC when the expected value is supplied and prints an explicit warning when it is not. This manual recipe is exercised end to end by an automated test using nothing but those three tools, so the documentation cannot drift away from the format.

12.5Expected recovery cost

Recovery remains deliberately sequential and should be planned in minutes to hours depending on scope. TOC discovery scans backwards from end-of-data using one small 256 KiB sniff per candidate rather than reading candidate payloads in full. The current 128 GB chunk target bounds random single-chunk tape streaming to roughly tens of minutes on the measured hardware path (about 18–20 minutes at ~117 MB/s), rather than the multi-hour amplification of the former near-terabyte chunks. Whole-project recovery is still dominated by total LTO streaming volume and cartridge changes.

13Failure handling and state machines

13.1The two state machines

run PLANNING -> RESERVED -> PRODUCING -> DRAINING -> CLOSING -> CLOSED
 \-> DENIED (no reservation granted)
 FAILED / CANCELLED (signed abort protocol)

chunk (bus marker) PRODUCED -> READY -> CLAIMED -> DONE (ERROR on failure)
 (tape segment) WRITING -> WRITTEN -> VERIFIED (ABANDONED on recovery)

13.2Crash recovery — strategy A

The segment row is written before the tape write. On restart, the daemon abandons every segment left in WRITING or WRITTEN, accounting their consumed capacity conservatively in the same transaction, and abandons every close artefact left in WRITING. Their chunks are re-claimed and rewritten.

The system is honest about the physical consequence: the abandoned copy remains physically on the append-only cartridge. What is guaranteed is that the catalogue never references a duplicate — the TOC and all restore paths use only VERIFIED rows. Capacity accounting counts the orphan, so the space is not double-booked.

At startup, after both the singleton and the generation fence are held, every unresolved non-terminal CLAIMED marker is requeued immediately rather than waiting out the six-hour TTL — safe precisely because the fence guarantees no older worker can still be touching tape.

13.3Terminal fencing

Terminal markers are a safety fence, never destructive authority. The distinction is deliberate and was introduced after a rejected release:

  • The mere existence of run.ABORTED, run.ABORT_DONE, run.CLOSED or run.DENIED — even unsigned or torn — stops all new tape I/O for that run. Fencing must not depend on cryptography being enabled.
  • Deleting ciphertext or staging, by contrast, happens only after the corresponding terminal marker has been signature-verified and path-bound. An unsigned run.ABORTED can stop tape I/O; it cannot cause a deletion or produce an ABORT_DONE. A dedicated signing-enabled regression test proves exactly this.
  • CLOSED is a hard fence for new writes but still permits one protocol-level idempotency: reconstructing a DONE receipt for a chunk whose two copies are already VERIFIED. ABORTED and DENIED permit no chunk handling at all.

13.4The abort protocol

On failure the cluster marks the run FAILED and publishes a signed run.ABORTED. The tape server verifies it, orphans all of that run's segments, releases the reservation so the pairs become reusable, removes every pending data-path marker and staged ciphertext, and acknowledges with run.ABORT_DONE. Consumed tape is left honestly accounted as orphan. The cluster waits for the acknowledgement before cleaning the bus; if it does not arrive within the timeout, the bus directory is preserved for daemon recovery rather than removed.

This protocol is what prevents the two historical failure shapes: runs stuck forever in PRODUCING, and reservations that only released when their TTL expired.

13.5The silent-failure discipline

Several defects found in this system shared one shape: an error that produced a wrong result without an error message. The countermeasures now applied throughout are worth listing, because they are the design principle a reviewer should test against.

13.6Cancellation

A detached local job runs in its own session and process group. bric cancel JOB_ID sends SIGTERM to the whole group, so the producer's own traps mark the active run FAILED and publish the signed abort rather than leaving it wedged. Job state, exit code and end time are recorded in the job metadata file.

14Logging, audit and notifications

14.1Operational logging is a correctness requirement

Invariant I10 treats logging as part of correctness. With BRIC_REQUIRE_LOGGING=1, a process refuses to proceed when neither its primary nor fallback destination can persist structured events.

Root/system components use the system log tree under /var/log/bric. Activated researchers use a central per-user primary tree, normally /var/log/bric/users/<user>, and a private fallback under ~/.bric/log. The per-user central directory is owned by the user but ACL-isolated from broad owning groups and grants the configured BRIC administrator group read/traverse access. Runtime-created files are normalized to the same isolation policy; if ACL enforcement on the central destination fails, logging falls back rather than leaving an ambiguously protected central file.

14.2The BRICLOGv1 record

Every structured record is one line of exactly 23 pipe-delimited fields:

BRICLOGv1|time|host|role|user|component|pid|ppid|level|event|run|project|
chunk|copy|drive|vt|attempt|rc|duration_ms|bytes|slurm_job|slurm_task|message

Values are line-safe, timestamps are UTC ISO-8601 with milliseconds, and the version prefix is mandatory. Event paths recompute the UTC day for each record so a long-running daemon naturally rolls over at midnight. Raw stdout/stderr remain separate process-lifetime files. Structured primary-log failure first persists the triggering event on the fallback and emits a LOG_FAILOVER breadcrumb plus a stderr warning.

14.3Audit trail

Both catalogues carry an audit_log table with timestamp, actor, action, object, result and detail. The cluster records user-facing actions — run requested, reserved or denied, run closed, restore requested and completed, user registered and user activated. The tape server records physical actions — reservation, segment verified, verification failure, tape full, close, abort and re-verification. Structured operational logs provide an additional chronological record of system activity.

14.4Notifications

Backup start, completion, denial and failure, and restore start, completion and failure, produce a notification. E-mail is opt-in (BRIC_NOTIFY_MAIL=auto, address derived as <owner>@<domain>); the structured notification log line is always written and records whether mail was sent, failed, skipped or not attempted. Every statement in the notification path is armoured against failure, because the function runs inside scripts under set -e invoked by non-root users, and an unprotected line once killed every run immediately after the reservation was granted.

Restore notification requirement

When a restore completes with metadata_fidelity=DEGRADED, the user-facing communication must explicitly say “data integrity: verified” when destination verification passed, separately say “metadata fidelity: degraded”, and explain that ACLs/xattrs or identity mappings could not be reproduced exactly. It must also explain that files may inherit the destination's current access policy. The words “partial restore” or an unexplained “degraded” result are insufficient because they can be misread as file-content corruption.

The current recovery-candidate notification records the aggregate result and metadata-fidelity state. The longer explanatory wording above is the required operational interpretation and should be incorporated directly into the final user notification before promotion.

15Web interface

A small optional web interface exists for researchers who do not use the command line. Its security model is deliberately simple and worth stating precisely, because "web interface" and "genomic archive" in the same sentence invites scrutiny.

  • It is launched as a Slurm job by the user, on the same pattern as the site's RStudio template, and is reached through an SSH tunnel. The tunnel is the network boundary.
  • The process runs with the launching user’s UID. Every bric command therefore inherits that user’s KU identity, filesystem permissions and access to the protected personal key in the user’s cluster home. There is one session per user and no second application login.
  • Each URL carries a random session token as a capability path segment; a request without it receives 403. This is defence in depth in case someone on the cluster network reaches the node's port directly.
  • The session expires with the job's Slurm walltime.
  • Implementation is a single Python 3 file using only the standard library — no third-party packages. It is confined to the UI layer and does not touch the recovery path.
  • All mutations go through the bric CLI invoked with an argument vector, never shell=True, so shell injection is not possible. The catalogue is opened read-only through a SQLite URI. Project names are validated against the same charset as the shell library.
  • Destructive operations are not exposed. The interface can start a backup, show the user's own runs, and restore.

Two residual points for the reviewer: the capability token appears in the URL and can therefore land in browser history or a proxy log — acceptable behind an SSH tunnel with a job-lifetime session, but worth knowing; and the directory browser lets the user navigate the filesystem, bounded exactly by their own UID's permissions, granting nothing the shell would not.

16Deployment and operations

16.1Installation

bric-setup.sh initialises a host and is safe to re-run: schema creation uses IF NOT EXISTS, cartridges are inserted with INSERT OR IGNORE so a cartridge in use is never reinterpreted, the master key is never rotated, user escrows are idempotent, no DROP is ever issued, and any existing catalogue is copied to a timestamped backup before being touched. --dry-run previews without writing.

./bric-setup.sh --role slurm # gate host: cluster catalogue, master key, config, man page, links
./bric-setup.sh --role tape # tape host: tape catalogue, inventory, systemd unit
./bric-setup.sh --role all # single-host staging for end-to-end proof

Setup verifies the host's capabilities rather than assuming them: it proves that SQLite WAL works, and that OpenSSL can both sign and verify — not merely generate a key, because generating an Ed25519 key succeeds on OpenSSL 1.1.1 while signing it is impossible there, and a keygen-only probe once reported success on a host that could not sign. Real barcodes must be supplied through BRIC_BARCODES_FILE; the pattern fallback exists only for staging.

The tape host also receives a systemd unit that runs the daemon as root with RequiresMountsFor=/mnt/data, a syntax check of the daemon script as a start pre-condition, a preserved runtime directory, SIGTERM with a 120-second stop timeout, and restart-on-failure with a burst limit.

16.2Configuration model

One file per host, /etc/bric/bric.conf, root-owned, mode 0644. Precedence is environment > file > built-in defaults. The file is parsed, never executed: only lines of the form BRIC_NAME=value are honoured, so it cannot run code. BRIC_FAULT_* keys are actively refused by the loader, because fault injection must never be persistable. BRIC_CONFIG=none disables loading entirely, which is how the test suite achieves hermeticity.

16.3Versioning and in-place updates

A complete installation records its software version in /opt/bric2/RELEASE, readable with bric version or bric-update --current. Updates are applied from a freshly extracted package, never from the installed tree:

sudo ./bric-update --target /opt/bric2 # role read from /etc/bric/bric.conf

The updater verifies the package manifest, refuses to run while archive or tape work is active, replaces only managed static files whose content actually changed, backs up every replaced file under /var/backups/bric2, updates host integrations (command links, man page, systemd unit), and preserves catalogues, configuration, keys, logs, user homes and the QNAP bus. It reads the host role from the configuration file, refuses a conflicting role argument, and refuses to proceed if a foreign or extracted-tree daemon remains active after systemd has been asked to stop the service.

17.3Security observations and recommendations

The following observations remain relevant to deployment and review.

O-1 · Cluster-side marker signing is shared with archive-user processes — architectural

When signing is mandatory, user-side archive processes must be able to read the cluster signing private key. The mechanism therefore authenticates “a process possessing the cluster-side key”, not a privileged service distinct from every onboarded user. It protects against a QNAP-only/unauthorised writer without that key, but not against a malicious onboarded user. A stronger boundary would require a privileged signing broker or per-user identities.

O-2 · Verify require_bus_signing=1 after deployment — deployment check

The schema default is 0; setup enables enforcement only when the required keys are already present. Production acceptance should verify the catalogue value on both cluster and tape hosts.

O-3 · Derived HMAC keys appear in process arguments — code hardening recommended

Some OpenSSL HMAC calls pass a derived authentication key via argv. This does not reveal the independent encryption key, but another process able to inspect the command line at the right moment could obtain a MAC key. A non-argv key interface or in-process HMAC implementation would remove that exposure.

O-4 · Institution master-key custody is an operational control

The software protects the master-key file with root-only permissions and never sends it to tape, QNAP or user jobs. Backup/offline custody, break-glass approval, succession and recovery ceremony must be defined operationally by BRIC/KU.

O-5 · QNAP permissions must match the real trust model

Local-mode archive users intentionally write their own bus objects, so NFS host allow-lists, UID/GID mapping/squash, setgid/ACL policy and the actual set of writable principals must be verified. Payload confidentiality does not make protocol availability/integrity irrelevant.

O-6 · Metadata fidelity is destination- and identity-dependent

Current archives preserve ordinary regular-file permissions, mtime and selected ACL/xattr representations where the source exposes them, including user.*, POSIX ACL information and system.nfs4_acl. That is a preservation statement, not a promise that a future destination can replay every item. Destination filesystem capabilities, export/access-zone policy, ACL inheritance, directory services and identity mappings can all change independently over the archive lifetime.

UID/GID ownership is not restored; regular-file setuid/setgid/sticky bits are deliberately removed; SELinux/security/trusted and unrelated system xattrs are outside the archival contract; sparse allocation topology is not guaranteed. ACLs add a second long-term limitation: an archived principal may become UNMAPPABLE even when the destination technically supports the ACL model. Full metadata fidelity therefore requires both a compatible destination capability and meaningful identity resolution at restore time. These are data-owner-visible semantics rather than hidden implementation details.

17.4Accepted residual risks

RiskRationale for acceptance
In-place marker replay. Path binding and domain separation prevent a signed marker from being moved; they do not prevent re-placing the identical file and its signature at their original location. Markers are write-once with atomic rename, every operation is idempotent (a re-published READY for an already-verified chunk is a no-op, not a duplicate), and write access to the bus is restricted. Full anti-replay would require monotonic per-run nonce state checked at every marker — cross-cutting state for an attacker who has write access to the QNAP but is not the cluster, which is outside the model and contrary to the simplicity the recovery promise depends on.
Orphaned blocks on append-only media after a crash or abort. Physically unavoidable on append-only media. What is guaranteed is that the catalogue and the TOC never reference them, and that their consumed capacity is honestly accounted.
Hard links multiply tape space and restore as separate copies. Deduplication would introduce a cross-file dependency that breaks the "each segment is independently recoverable" invariant.
Allocation topology is not guaranteed for sparse files. The source protocol cannot expose it reliably. Byte content is authoritative and the limitation is recorded explicitly in the encrypted catalogue rather than being left implicit.
Loss of all recoverable user-key copies and the institution master key is unrecoverable. This is the confidentiality design. Normal operation has a protected cluster/home key, a user-held USB copy and encrypted institutional escrow; if all usable plaintext copies are gone and the master key cannot unwrap escrow, the archive cannot be decrypted.
Historical ACLs may be preserved but not replayable years later. The destination may not support the archived ACL/xattr model, may intentionally forbid clients from replacing security metadata, or may no longer resolve the original UID/GID, SID, group, domain or realm. BRIC separates verified file contents from metadata fidelity and records degraded recovery rather than claiming equivalence. Current destination policy/inheritance may be operationally correct without being historically identical.
Correctness depends on POSIX semantics of the shared export. Documented explicitly (§4.5); must be re-validated if the staging appliance or its export configuration is ever replaced.

DGlossary

Archive vs backup
An archive is judged by recoverability without its original environment; a backup by restore speed into an existing one. BRIC is the former.
Bus
The shared QNAP NFS directory tree used for all communication and payload transport between the two hosts. Transient, opaque, never authoritative.
Chunk
One unit of archived payload: an independent encrypted tar archive, or a raw byte range of one oversized file.
Segment
One physical copy of one chunk on one cartridge, at one file number.
Run
One invocation of bric backup. The first run of a project is the initial archive; later runs are self-contained appends.
Marker
A small text file on the bus used as a protocol message, published by atomic rename, optionally with a detached signature.
PRIMARY / BACKUP
The two roles in a cartridge pair. PRIMARY is intended to remain on site; BACKUP is intended for off-site storage when full.
Pair
Two cartridges, one of each role, holding identical copies of a project's segments.
Semantics B
The reservation rule: tape is reserved before any ciphertext is produced. Insufficient media means stop, not partial production.
Strategy A
The crash rule: record write intent before touching tape; on restart abandon interrupted writes rather than interpreting the tail.
Encrypt-then-MAC
Compute the MAC over the ciphertext and verify it before decrypting. Never decrypt unauthenticated data.
Escrow
A user's personal key, encrypted and authenticated under the institution master key, stored centrally and copied to every project cartridge as ciphertext.
Break-glass
Administrator recovery of a user's data using the institution master key, without that user's participation. Offline custody is an operational policy, not a software-enforced property.
TOC
The plaintext table of contents appended last on each cartridge at every close, mapping tape file numbers to their contents. The latest valid one wins.
Generation fence
A blocking lock inherited by every tape worker, which a new daemon must acquire before recovery, guaranteeing no surviving worker from an older generation is still touching hardware or catalogue.
Crypto-erase
Rendering archives computationally unreadable by destroying the personal key and all recoverable escrow copies. This is a technical property; legal sufficiency for a particular deletion obligation is a separate governance decision.
Logical root
A stable one-component name bound to a canonical source path and used to address files across multiple CLOSED runs without exposing the original absolute source path.
Data integrity
The statement that restored file contents are present and match the archived plaintext checksums. It is independent of ACL/xattr fidelity.
Metadata fidelity
The degree to which archived non-payload metadata — such as mode, mtime, ACLs and selected xattrs — has been reproduced with equivalent semantics on the destination.
Degraded restore
A restore whose file contents satisfy the required integrity checks but whose metadata fidelity is explicitly incomplete. It is not a synonym for corrupted or partially restored file contents.
UNSUPPORTED
A metadata outcome meaning that the destination cannot represent or does not permit the requested metadata operation.
UNMAPPABLE
A metadata outcome meaning that the destination supports the metadata model but one or more archived identity principals cannot be resolved or mapped meaningfully in the current identity environment.
Progressive restore
Reverse-bus protocol that stages one encrypted chunk at a time, uses signed progress heartbeats and requires a signed CONSUMED acknowledgement before the next chunk is staged.
