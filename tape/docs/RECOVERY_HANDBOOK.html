0 · Emergency start — you found tapes and need the data

You need exactly two things:

  1. The tapes. Ideally both tapes of each pair, but one tape of a pair usually holds a complete copy of everything.
  2. One key. Either the project owner's user key (a single line of base64 text, e.g. from a file named <username>_user_key.txt), or the institution master key (same shape). The master key unlocks copies of all user keys — see Section 8.

You also need hardware and software that were deliberately chosen to still exist decades later: an LTO tape drive able to read LTO-9 media, and a Unix-like system with dd, mt, tar, openssl, sha256sum and sqlite3. Nothing proprietary. No BRIC software is required (Section 7 is the fully manual procedure), though each tape carries a small plaintext recovery kit including a ready-made script.

The 60-second summary of what you will do:

  1. Read the last text file on the tape: it is a plaintext index (the TOC) telling you which tape-file number holds what.
  2. Pull catalog_project.enc off the tape, decrypt it with a key derived from the user key: it is a plain SQL text dump — the complete map of every archived file.
  3. For each data chunk you need: read it off the tape, verify its HMAC first, then decrypt and unpack.

Everything below teaches you enough to do this even if all you have is this document, the tapes, and a key.

SECTION 1What this system is (the thesis)

BRIC Archive 2.0 is a cold archive, not a backup system. The distinction drives everything:

  • A backup protects a live system and assumes the infrastructure that made it still exists when you restore.
  • An archive assumes the opposite. The design promise, verbatim from the architecture document, is: the genomic data must be recoverable 10–15 years from now from the tapes and the user key alone — without the compute cluster, without the central catalog database, without the archiving daemon, without the staging storage, and without BRIC or the university necessarily existing anymore.

Every other property of the system — the on-tape catalogs, the plaintext recovery kit, the pinned cryptographic parameters, the self-describing chunks — is the intrinsic cost of that promise. The system was built and reviewed under an explicit rule: any feature that does not serve the promise or answer a concretely observed operational failure is a candidate for removal, not an addition.

Why it matters to you, the recoverer: the system was designed for exactly your situation. There are three independent ways in (Sections 6, 7, 8), redundant copies of both the data and the maps to the data, and no step that requires software more exotic than openssl and tar.

SECTION 2The physical layer: tapes, pairs, and how to read them

2.1 The cartridges

The media are LTO-9 cartridges, 18 TB native capacity each, labelled with 6-digit barcodes of the form NNNNNNL9. The barcode is not decorative — its parity encodes the tape's role:

Barcode parityRoleLocation policyPairing rule
Even (…0, …2, …4)PRIMARYKept on site (in the library)BACKUP barcode = PRIMARY barcode + 1.
Example: 000042L9 (PRIMARY) pairs with 000043L9 (BACKUP).
Odd (…1, …3, …5)BACKUPMoved off site when full
Configuration note: the parity convention is a configuration value (primary_parity=even in the tape catalog's config table). Even = PRIMARY is the production convention this document assumes. If a rebuilt catalog derives pairings that contradict the physical labels you observe, trust the physical inventory and the TOCs, not the derivation.

2.2 Two copies of everything

Every chunk was written twice: once to the PRIMARY tape, once to its BACKUP partner, each write independently read back and verified against the chunk's SHA-256 before being recorded. The two tapes of a pair are therefore near-mirrors of each other for the data they carry (their file numbering can differ — always trust each tape's own TOC). Consequences for you:

  • If one tape of a pair is lost, damaged, or unreadable, the other one alone is normally sufficient.
  • All recovery procedures in this document try PRIMARY first and fall back to BACKUP per chunk — a partially damaged pair can still yield a complete recovery ("auto-healing").

2.3 How data is laid out physically

A tape is a sequence of tape files separated by filemarks — this is the native structure of magnetic tape, older and more durable than any filesystem:

┌────────┬─FM─┬────────┬─FM─┬────────┬─FM─┬───────────────┬─FM─┬───────────────┬─FM─┬──────┬─FM─┬─ EOD │ file 1 │ │ file 2 │ │ file 3 │ │ file 4 │ │ file 5 │ │ ... │ │ │ chunk │ │ chunk │ │ chunk │ │ catalog_ │ │ catalog_ │ │ kit │ │ TAPE_TOC.txt │ blob │ │ blob │ │ blob │ │ project.enc │ │ system.enc │ │ files│ │ (last file) └────────┴────┴────────┴────┴────────┴────┴───────────────┴────┴───────────────┴────┴──────┴────┴────────────── FM = filemark (hardware end-of-file marker) EOD = end of data (the append point)

Key physical facts, all of which you need for manual reading:

Block size262144 bytes (256 KiB), written in variable-block mode (mt setblk 0). Read with dd bs=262144.
One file = one objectEach tape file is exactly one object: one encrypted chunk blob, or one catalog, or one kit file, or one TOC. A single dd stream; closing the Linux non-rewind tape device emits the one flushing filemark. Do not add a second mt weof.
File numbering1-based sequential position. "File number 7" means: rewind, skip 6 filemarks (mt fsf 6), read.
Append-onlyNothing on a tape is ever rewritten or erased. New data and new indexes are only appended at EOD. Whatever was true on the tape yesterday is still physically there today.
Multi-project, multi-runA tape can hold chunks of several archiving runs and (in principle) several projects; the catalogs and TOC tell them apart.

2.4 Reading the drive: the three commands you need

# The library changer is driven by mtx (a standard SCSI media-changer tool), the drive by mt.
# /dev/sg* = the changer's SCSI device; /dev/nst0 = the drive (n = non-rewinding: essential).

mtx -f /dev/sgX status                 # inventory: which barcode sits in which slot
mtx -f /dev/sgX load  SLOT 0           # move cartridge from SLOT into drive 0
mtx -f /dev/sgX unload SLOT 0          # put it back

mt -f /dev/nst0 setblk 0               # variable-block mode (always do this first)
mt -f /dev/nst0 rewind                 # go to file 1
mt -f /dev/nst0 fsf N                  # skip forward N filemarks (to file N+1)
mt -f /dev/nst0 eod                    # go to end of data (the append point)

dd if=/dev/nst0 of=out.bin bs=262144   # read ONE tape file (stops at the filemark)
If you have no library, a standalone LTO drive works: insert cartridges by hand and skip the mtx steps. If you have no drive at all, note that the LTO consortium's compatibility rule has historically been "a drive reads at least one generation back" — LTO-9 media should be readable in LTO-9 and LTO-10 drives. If you are far enough in the future that no such drive survives, data-recovery firms and computer museums maintain working units; the format below is fully documented so any raw block-level read of the tape can be reassembled.

SECTION 3What is on a tape — BRIC-FORMAT-V1, object by object

3.1 Chunk blobs (the data itself)

The unit of archiving is the chunk: a target of 128 GB of source data, encrypted as one opaque blob. There are two kinds, distinguished only in the catalog (the blobs look identical):

KindContents before encryptionHow it is restored
TAR_PARTA standard tar stream of whole files (many small/medium files packed together until 128 GB). Files are never split between two TAR_PARTs. The final TAR_PART of a run is the metadata chunk: all directories (including empty ones), directory permissions and mtimes, and symlinks.Decrypt, pipe to tar -x.
LARGE_FILE_CHUNKA raw byte-range slice of one single file larger than the chunk target (common for genomic files: BAM, FASTQ). The catalog records the file it belongs to (big_rel_path), the slice's position (chunk_index, 1-based, and offset_bytes) and the total number of slices.Decrypt each slice, concatenate in chunk_index order.

3.2 The encryption envelope of every blob

Every chunk blob and both catalogs use one identical, deliberately pinned recipe — the exact OpenSSL command line is part of the format definition:

# producing side (what was run in 2026):
tar -c ... | openssl enc -aes-256-cbc -pbkdf2 -iter 10000 -salt -pass file:PASSFILE  > chunk_0001.enc
# therefore the recovering side is, for all time:
openssl enc -d -aes-256-cbc -pbkdf2 -iter 10000 -pass file:PASSFILE -in chunk_0001.enc | tar -x
cipheraes-256-cbc — AES, 256-bit key, CBC mode. Integrity is provided externally by the HMAC (next row), never by the cipher.
KDFPBKDF2, iteration count 10000, explicit. The digest is SHA-256.
salt8 random bytes, embedded in the blob itself in OpenSSL's standard Salted__ header (first 16 bytes of every blob: the ASCII Salted__ magic + 8 salt bytes). Nothing about the salt needs to be stored anywhere else.
MACHMAC-SHA256 computed over the ciphertext (Encrypt-then-MAC). The expected value for each chunk is stored in the catalog column chunks.payload_hmac. Verify before decrypting, always.
content hashSHA-256 of the ciphertext in chunks.payload_sha256, and in the on-tape TOC — a keyless integrity check usable even before you have any key.
Why CBC + HMAC and not an all-in-one AEAD mode like AES-GCM: the openssl enc command-line tool — the one tool most likely to exist unchanged on any Unix system decades from now — does not support GCM. CBC-with-explicit-external-HMAC is the composition that (a) any generation of OpenSSL ≥ 1.1.1 performs identically, (b) can be verified and even re-implemented by hand from this document, and (c) is cryptographically sound as long as the MAC is checked first, which every reader in this system does. All parameters are pinned in the command line, recorded per-chunk in the catalog, and repeated in the plaintext kit on every tape, so a future BRIC-FORMAT-V2 could change them while V1 tapes remain forever openable.

3.3 The recovery artifacts appended at every close

When a run finishes, the following files are appended to every tape the project touches, in this order, followed by a fresh TOC as the very last file:

#FileEncrypted withWhat it is
1catalog_project.encthe owner's user keyThe complete map of this project: an SQL text dump of the tables projects, runs, chunks, files, project_tapes, plus a placement table (run_id, chunk_no, copy_role, volumetag, file_number) that says exactly which tape file holds which chunk copy. Once decrypted it is human-readable SQL; load it into sqlite3 or even read it with your eyes.
2user_key_escrow.v1already wrapped with the institution master keyA small project-bound text envelope containing the owner's authenticated v2:<hmac>:<ciphertext> escrow. It is ciphertext only: the user job copies it from the cluster catalog without ever reading the master key. An administrator with the master can unwrap it and then open catalog_project.enc.
3restore_from_tape.sh— plaintext —A minimal, dependency-free shell script that HMAC-verifies and decrypts one chunk blob given the user key. It is the executable form of Section 7.
4README_RECOVERY.txt— plaintext —A condensed version of this document: format name, pinned crypto parameters, the key-derivation recipe, and the verify-then-decrypt commands.
5schema.sql— plaintext —The catalog schema, so the SQL dumps can be rebuilt into a live database even if the schema is otherwise lost.
6TAPE_TOC.txt— plaintext —The cumulative index of this tape (Section 4). Always the last file after a close.
Why this separation: the data owner recovers with their personal key and nothing else. The institution recovers a lost personal key from the small authenticated escrow, but the master key never enters a user-owned Slurm job and never reaches the tape server. The plaintext scripts/schema make the format self-describing. Legacy tapes may contain catalog_system.enc; the DR tool keeps that read path solely for backward compatibility.

SECTION 4The table of contents on tape (TOC)

The TOC is a small plain-text file with a fixed, deliberately parser-friendly grammar. Its header line is the magic string that identifies it:

# BRIC tape TOC v1
volumetag=000042L9
run_id=mouseproj__20260708T101500Z__0003
project=mouseproj
file|kind|run_id|chunk_no|copy_role|filename|sha256
1|CHUNK|mouseproj__20260708T101500Z__0003|1|PRIMARY||3a92f0c1…<64 hex chars>
2|CHUNK|mouseproj__20260708T101500Z__0003|2|PRIMARY||b81d77e4…
7|ARTIFACT|mouseproj__20260708T101500Z__0003|||catalog_project.enc|9c01ab52…
8|ARTIFACT|mouseproj__20260708T101500Z__0003|||user_key_escrow.v1|44e0d9f3…
9|ARTIFACT|mouseproj__20260708T101500Z__0003|||restore_from_tape.sh|…
10|ARTIFACT|mouseproj__20260708T101500Z__0003|||README_RECOVERY.txt|…
11|ARTIFACT|mouseproj__20260708T101500Z__0003|||schema.sql|…

Rules you can rely on:

  • Data lines match ^[0-9]+|; everything else is header. Fields are pipe-separated, 7 per line. CHUNK lines leave filename empty; ARTIFACT lines leave chunk_no and copy_role empty.
  • The TOC is cumulative: each new TOC lists every verified chunk and artifact on the tape, across all runs, not just the latest run. The last valid TOC on a tape supersedes all earlier ones — that is the whole indexing model ("latest TOC wins").
  • The first column is the tape file number: your mt fsf target.
  • The last column is the SHA-256 of that tape file's content — verify every read against it.
  • The TOC never contains a user path or filename from inside the data. That privacy boundary is enforced at write time: file names live only inside the encrypted project catalog.

4.1 Finding the latest TOC

After a clean close the TOC is simply the last file before EOD. But a later run may have appended chunk blobs after the last TOC before being interrupted — so the robust procedure, and the one the recovery tooling implements, is: scan backwards from EOD toward file 1; the first file whose first line is # BRIC tape TOC v1 is the authoritative TOC. Sniff each candidate by its first 256 KiB block only (candidates that are not TOCs are giant chunk blobs; do not read them whole). If a TOC's header is unreadable or corrupted, keep scanning backwards: an earlier TOC is still valid for everything it lists — you lose only what was archived after it.

SECTION 5Cryptography: keys, derivation, escrow

5.1 The two secrets

SecretShapeUnlocks
User key (one per data owner)One line of text: 32 random bytes, base64-encoded (44 characters ending in =). Issued at registration; the owner keeps their own copy.That owner's chunk blobs and catalog_project.enc.
Master key (one per institution)Same shape, held only by administrators/offline custody.Authenticated user_key_escrow.v1 artifacts and catalog escrows. It never decrypts data directly and is never needed by normal backup jobs.

5.2 Deriving the working keys — do this by hand

From one user key, two purpose-bound working keys are derived with nothing more exotic than sha256sum. The suffixes are literal ASCII, no spaces, no newline before the suffix:

USER_KEY='<the one-line base64 secret>'
ENC_PASS=$(printf '%s:encryption'     "$USER_KEY" | sha256sum | awk '{print $1}')
HMAC_KEY=$(printf '%s:authentication' "$USER_KEY" | sha256sum | awk '{print $1}')
  • ENC_PASS (64 hex chars) is the passphrase given to openssl enc via -pass file: — note it is a passphrase fed to PBKDF2, not the raw AES key itself.
  • HMAC_KEY (64 hex chars) is the key for openssl dgst -sha256 -hmac.
Why domain-separated SHA-256 instead of a fancier KDF here: the derivation must be reproducible by hand, from memory of this one paragraph, on any machine. Two different suffixes guarantee the encryption passphrase and the authentication key can never be confused or substituted for one another, and sha256sum is the single most universally available cryptographic tool in existence. The actual key stretching happens afterwards inside PBKDF2.

5.3 Key escrow (the break-glass copy of user keys)

At registration, each user key is wrapped with the master key (key escrow) and stored in the system catalog column users.key_escrow in this exact format:

v2:<hmac_hex>:<ciphertext_base64>

# where:
ciphertext_base64 = openssl enc -aes-256-cbc -pbkdf2 -iter 10000 -a -A -salt -pass file:master.key   < user_key
hmac_hex          = HMAC-SHA256 over the base64 STRING, keyed with sha256hex(MASTER_KEY + ":escrow-auth")

The cluster stores this value in users.key_escrow. At project close the ordinary user job copies that already-encrypted value into user_key_escrow.v1 together with the project and owner identifiers. No master-key operation happens in the user job. The artifact itself is hashed in the tape TOC; admin recovery also verifies project/owner binding against the decrypted project catalog.

To unwrap (given the master key in master.key):

ESCROW='v2:...'                                   # decoded from user_key_escrow.v1 (or from legacy catalog_system)
HK=$(printf '%s:escrow-auth' "$(cat master.key)" | sha256sum | awk '{print $1}')
HM=${ESCROW#v2:}; HM=${HM%%:*}                    # the stored hmac
CT=${ESCROW#v2:*:}                                # the base64 ciphertext
test "$(printf '%s' "$CT" | openssl dgst -sha256 -hmac "$HK" | awk '{print $NF}')" = "$HM" \
  || { echo "escrow TAMPERED/CORRUPT — stop"; exit 1; }
printf '%s' "$CT" | openssl enc -d -aes-256-cbc -pbkdf2 -iter 10000 -a -A -pass file:master.key
# output = the user key, one line
Legacy escrows from before format v2 are bare multi-line base64 without the v2: prefix and without an HMAC; decrypt them with the same command but -a instead of -a -A, accepting that they are unauthenticated. The escrow only exists for a user if require_user_escrow=1 was active at that user's registration — the enforcement of this at registration time is what makes break-glass recovery possible at all.

5.4 What is deliberately NOT protected

Honesty about the threat model, so you don't look for guarantees that were never made: the plaintext TOC and kit files are integrity-covered by SHA-256 (in the TOC and, for the TOC itself, in the catalog databases) but not by any key — an adversary with write access to the physical tapes could forge them. The system's threats were media decay, infrastructure loss and key loss, not a tape-forging adversary; the encrypted layers (blobs, catalogs, escrow) are the ones with keyed authentication.

SECTION 6Recovery path A — with the BRIC scripts (recommended)

If you have the BRIC source tree (from the institution's repositories, from an admin machine, or reconstructed from the kit files), the disaster-recovery tool does everything in this document automatically. It needs no database, no daemon, no network — only the tapes and one key:

# Whole project, user key path:
cluster/scripts/bric-dr-from-tapes.sh \
    --project  MYPROJECT \
    --user-key-file /path/to/user_key.txt \
    --dest     /recovery/output \
    [--tapelib /path/to/simulated/library]      # omit on a real drive/library

# One single file only:
bric-dr-from-tapes.sh --project MYPROJECT --user-key-file KEY --dest OUT --file 'raw/sample_007.bam'

# Break-glass (no user key; institution master key instead):
bric-dr-from-tapes.sh --project MYPROJECT --master-key-file /path/to/master.key --dest OUT
Scripted DR bundle dependency. Keep cluster/scripts/lib_restore_txn.sh and cluster/libexec/bric-file-metadata with bric-dr-from-tapes.sh. The scripted DR tool sources it to provide crash-safe destination permission handling. The fully manual recovery path in Section 7 does not depend on this helper.

What it does, in order (so you can supervise it): scans every tape backwards from EOD for the latest valid TOC (sniffing candidates by their first block); locates and SHA-verifies catalog_project.enc against the TOC before decrypting it; loads the catalog; then for every chunk of every run (runs in chronological order — the latest version of a file wins), reads the PRIMARY copy, verifies SHA-256 and HMAC, falls back to the BACKUP copy on any failure, decrypts, unpacks tar parts and reassembles large files in slice order, restores the directory-metadata chunk last, and finally re-verifies every recovered file against its recorded plaintext SHA-256. It refuses to decrypt anything whose HMAC does not verify.

The related tool bric-tape-rebuild-catalog.sh reconstructs the tape server's operational database from the tapes alone (same TOC scan) — needed only if you intend to resume operating the system, not to recover data. Run it with --verify before ever writing to rebuilt tapes.

SECTION 7Recovery path B — fully manual, no BRIC software at all

This is the path the whole system was designed to make possible. Tools required: mt, mtx (library only), dd, sha256sum, openssl, tar, sqlite3, awk. Work on a machine with enough scratch disk for at least one chunk (~1 TB) plus your recovered data.

Step 1 — Inventory and mount

mtx -f /dev/sg3 status                      # note which slots hold which barcodes
mtx -f /dev/sg3 load 12 0                   # load the PRIMARY (even barcode) of your pair
mt  -f /dev/nst0 setblk 0

Step 2 — Find the latest TOC (backward scan)

# Count how many files the tape holds by seeking to EOD, then probe backwards.
# Sniff each candidate by ONE block only — non-TOC candidates are ~1 TB blobs.
mt -f /dev/nst0 rewind
N=<highest file number>                     # if unknown: probe forward with fsf until EOD
for n in $(seq "$N" -1 1); do
    mt -f /dev/nst0 rewind
    [ "$n" -gt 1 ] && mt -f /dev/nst0 fsf $((n-1))
    dd if=/dev/nst0 of=/tmp/sniff bs=262144 count=1 2>/dev/null
    if [ "$(head -1 /tmp/sniff | tr -d '\0')" = "# BRIC tape TOC v1" ]; then
        mt -f /dev/nst0 rewind; [ "$n" -gt 1 ] && mt -f /dev/nst0 fsf $((n-1))
        dd if=/dev/nst0 of=TOC.txt bs=262144 2>/dev/null
        echo "TOC is tape file $n"; break
    fi
done

Step 3 — Pull and decrypt the project catalog

# From TOC.txt, read the ARTIFACT line for catalog_project.enc: its file number and sha256.
awk -F'|' '$2=="ARTIFACT" && $6=="catalog_project.enc" {print $1, $7}' TOC.txt
# -> e.g.:  14  9c01ab52…      read tape file 14:
mt -f /dev/nst0 rewind; mt -f /dev/nst0 fsf 13
dd if=/dev/nst0 of=catalog_project.enc bs=262144 2>/dev/null
sha256sum catalog_project.enc               # MUST equal the TOC's sha — else use the other tape

USER_KEY='<the owner’s one-line secret>'
ENC_PASS=$(printf '%s:encryption'     "$USER_KEY" | sha256sum | awk '{print $1}')
HMAC_KEY=$(printf '%s:authentication' "$USER_KEY" | sha256sum | awk '{print $1}')
printf '%s' "$ENC_PASS" > pass.txt && chmod 600 pass.txt

openssl enc -d -aes-256-cbc -pbkdf2 -iter 10000 -pass file:pass.txt \
        -in catalog_project.enc -out catalog_project.sql
# catalog_project.sql is PLAIN TEXT — you can literally read it. Load it:
sqlite3 cat.db < catalog_project.sql
If openssl prints bad decrypt: wrong key, or the recipe was typed with a wrong parameter (the iteration count and -pbkdf2 are mandatory), or the file failed its SHA check and is corrupt — try the same artifact from the partner tape.

Step 4 — Map your data

# What files exist, and in which run? (a project archived twice has two runs; the LATEST run
# holds the newest version of any file present in both)
sqlite3 cat.db "SELECT run_id FROM runs ORDER BY run_id;"          # lexicographic == chronological
sqlite3 cat.db "SELECT rel_path, size_bytes, sha256_plain FROM files WHERE run_id='<RUN>';"

# For each chunk of that run: what kind, and WHERE is it on tape?
sqlite3 cat.db "SELECT c.chunk_no, c.type, c.chunk_index, c.big_rel_path, c.payload_sha256, c.payload_hmac,
                       p.copy_role, p.volumetag, p.file_number
                FROM chunks c JOIN placement p
                  ON p.run_id=c.run_id AND p.chunk_no=c.chunk_no
                WHERE c.run_id='<RUN>' ORDER BY c.chunk_no, p.copy_role DESC;"

(The placement table and the TOC agree; use whichever is more convenient. The TOC of each tape is authoritative for file numbers on that tape.)

Step 5 — For every chunk: read, verify, decrypt, place

# -- read the chunk’s PRIMARY copy (from placement: volumetag + file_number) --
mt -f /dev/nst0 rewind; mt -f /dev/nst0 fsf $((FILE_NUMBER-1))
dd if=/dev/nst0 of=blob.enc bs=262144 2>/dev/null

#  -- verify BEFORE decrypting (both checks; on ANY failure, retry with the BACKUP copy) --
test "$(sha256sum blob.enc | awk '{print $1}')" = "$PAYLOAD_SHA256"   || { echo corrupt; try backup; }
test "$(openssl dgst -sha256 -hmac "$HMAC_KEY" blob.enc | awk '{print $NF}')" = "$PAYLOAD_HMAC" \
                                                                      || { echo tampered; try backup; }
# -- decrypt and place --
# TAR_PART:
openssl enc -d -aes-256-cbc -pbkdf2 -iter 10000 -pass file:pass.txt -in blob.enc \
  | tar -C /recovery/out -xp --no-same-owner --delay-directory-restore -f -
# LARGE_FILE_CHUNK (slices of one big file; chunk_index=1 first, then append in order):
openssl enc -d -aes-256-cbc -pbkdf2 -iter 10000 -pass file:pass.txt -in blob.enc \
  >> "/recovery/out/$BIG_REL_PATH"        # truncate the file first when chunk_index==1
Order matters, for one reason: the final TAR_PART of every run is the metadata chunk — it restores directory permissions, which may be restrictive (read-only "frozen" dataset directories are common in genomics). Extract it last, after every large file has been written into its directory, or the writes will fail with Permission denied for any non-root user. Processing chunks in ascending chunk_no order and doing the metadata chunk at the very end satisfies this automatically. If a project has several runs, process runs in ascending run_id order so the newest version of each file wins.

Step 6 — Verify (Section 13)

cd /recovery/out
sqlite3 ../cat.db "SELECT rel_path, sha256_plain FROM files WHERE run_id='<RUN>' AND sha256_plain!='';" \
| while IFS='|' read -r rel want; do
    got=$(sha256sum "$rel" | awk '{print $1}')
    [ "$got" = "$want" ] || echo "MISMATCH: $rel"
done

No output = every recovered file is bit-identical to what was archived.

SECTION 8Recovery path C — break-glass with the master key

Use this when no user key survives but the institution master key does. It is path B plus one preliminary stage:

  1. From the latest valid TOC, pull user_key_escrow.v1 and verify its SHA-256 against the TOC. Confirm the magic header, project= and owner= fields.
  2. Base64-decode escrow_b64=. The result is the exact v2:<hmac>:<ciphertext> value described in Section 5.3.
  3. Verify the escrow HMAC first, then unwrap it with master.key. The output is the user key: continue from Section 7 step 3. After decrypting catalog_project.enc, confirm that its project owner equals the owner declared in the escrow artifact.

The supplied bric-dr-from-tapes.sh --master-key-file ... performs all of these checks. For legacy tapes only, if no user_key_escrow.v1 exists, it falls back to the historical catalog_system.enc path.

An empty key_escrow means that user registered while escrow enforcement (require_user_escrow=1) was off — for that user there is no break-glass path; only their own key opens their data. This is by design: escrow is an institutional policy choice, and the system refuses to pretend a recovery path exists when it does not.

SECTION 9The living system — how the tapes got written

You do not need this section to recover data. It exists so a future maintainer (or a curious recoverer) understands the machine that produced what is on the tapes, and can judge whether the tapes are complete.

9.1 Topology

HPC CLUSTER (Slurm) TAPE SERVER ("brictape") ┌──────────────────────────┐ ┌──────────────────────────────┐ │ bric-plan (planner) │ │ bric-tape-daemon │ │ bric-chunk ×N (producers)│ shared │ pass 1: reservations │ │ bric-finalize │◄──"the bus"────►│ pass 2: drain chunks→tape │ │ bric-close (catalogs) │ QNAP NAS │ pass 3: close (catalogs, │ │ bric-restore │ (NFS export) │ TOC) │ └────────────┬─────────────┘ └──────────────┬───────────────┘ │ reads │ writes Isilon NFS (source data) HPE MSL3040 library, LTO-9 drives

The two servers never talk over a network protocol of their own. They communicate only through files on a shared directory (the bus): the cluster drops encrypted blobs and small signed marker files; the tape daemon claims work by atomically renaming a marker (.READY → .CLAIMED) — one winner, no distributed locks — writes the blob to both tapes of the pair, verifies each copy by reading it back, and publishes a .DONE receipt.

9.2 One archiving run, end to end

  1. Plan (bric-plan): walk the source tree, pack whole files into 128 GB TAR_PART chunks, slice oversized files into LARGE_FILE_CHUNKs, put all directories/symlinks/ permissions into a final metadata chunk. Record every file's size, mtime and (later) SHA-256. Reserve tape capacity with the daemon; exactly one active run per project is enforced by a conditional transactional insert.
  2. Produce (bric-chunk, parallel Slurm array): for each chunk, re-check the source is unchanged (the quiescence guard), stream tar|openssl (or dd|openssl) to the bus, compute SHA-256 and HMAC, re-check the source again, then publish the signed .READY marker. A sliding window bounds how many blobs sit on the bus at once.
  3. Drain (daemon): claim → write PRIMARY → read back and verify → write BACKUP → verify → .DONE → delete the blob from the bus. A crash at any point is safe: interrupted writes are abandoned (their tape space honestly accounted as orphaned) and the chunk is re-claimed; a copy that already verified is reused, not rewritten.
  4. Close (bric-finalize + bric-close + daemon pass 3): when every chunk is DONE, the cluster builds and encrypts both catalogs and the plaintext kit, hands them to the daemon with a signed manifest; the daemon appends every artifact to every tape the project touches, verifies each by read-back against the manifest, and finally appends the fresh cumulative TOC. Only then is the run CLOSED.

9.3 The two state machines

run    PLANNING → RESERVED → PRODUCING → DRAINING → CLOSING → CLOSED
                   └→ DENIED (no reservation)     FAILED / CANCELLED / *_ABORTED (signed)

chunk  (bus markers)   PRODUCED → READY → CLAIMED → DONE     (ERROR on failure)
       (tape segments) WRITING → VERIFIED                    (ABANDONED on crash recovery)

SECTION 10The invariants — the nine load-bearing guarantees

All correctness rests on these. They are few on purpose; break one and the system is broken regardless of everything else. (This is the contract every code change was reviewed against.)

#InvariantMeaning
1Claim = atomic renameTaking a chunk off the bus is a POSIX rename(): exactly one winner, no locks. (Requires the shared filesystem to provide atomic rename and coherent cross-host visibility — verified for the deployed NFS export, not guaranteed on arbitrary network filesystems.)
2One active run per projectEnforced transactionally; two concurrent backups of one project cannot coexist.
3Every chunk is independently verifiable and decryptableCiphertext + SHA-256 + HMAC + the key-derivation recipe travel together. A chunk opens and proves itself with the tapes and the key alone. This is the invariant that makes the thesis true.
4Tapes are append-only and multi-projectIndexes are never rewritten, only appended; the latest valid TOC (found scanning back from EOD) wins.
5Double copy PRIMARY + BACKUPEvery chunk on both tapes of a pair (even = PRIMARY onsite, odd = BACKUP offsite-when-full); readers fall back per chunk.
6Encrypt-then-MAC, verify before decryptNo blob or catalog is ever fed to openssl/tar before its integrity check passes.
7Singleton daemon + crash recoveryOne daemon at a time (flock); on start, interrupted writes are abandoned and re-done; a verified surviving copy is reused. No data loss, no duplicates.
8The central catalog is not the only truthEvery tape carries its own recovery kit and encrypted catalogs; the operational database is reconstructible from the tapes; the data is recoverable with no database at all.
9The format is fixed and versionedBRIC-FORMAT-V1: crypto parameters pinned in the command line, recorded per chunk and in the kit, so a future V2 can evolve without making V1 tapes unreadable.

SECTION 11Design decisions, and why each was made

Recorded so a future maintainer does not "fix" something that is load-bearing.

Why LTO tape at all. Multi-decade shelf life at rest, no power required, an open multi-vendor standard with a published roadmap, ~30-year media rating, and a cost per TB an order of magnitude below spinning disk for cold data. Cloud storage was rejected as the primary copy because the promise must survive the institution's contracts and vendors.
Why "archive, not backup" shapes everything. Backups optimize restore speed into a living system; archives optimize recoverability into an unknown future. Hence: self-describing tapes, hand-reproducible cryptography, plaintext kits, and no dependency of the recovery path on any BRIC component.
Why two full copies instead of parity/erasure coding. A mirrored pair is recoverable with zero mathematics and zero software: read the other tape. Erasure schemes save media but make recovery depend on the very tooling the thesis says may no longer exist.
Why the barcode-parity convention (even = PRIMARY). The pairing must be derivable from the physical label alone, so a rebuilt catalog — or a human with a printed inventory — can reconstruct pairs without any database. One parity had to be chosen; even-PRIMARY is set in config (primary_parity) and asserted by tests.
Why append-only tapes. Rewriting risks the one thing an archive cannot afford: destroying old truth to record new. Appending means every past state is still physically present; the cost — orphaned space from interrupted writes — is honestly accounted and accepted.
Why AES-256-CBC + external HMAC instead of AES-GCM. Explained in Section 3.2: openssl enc, the most future-proof tool available, does not do GCM; CBC+HMAC (Encrypt-then-MAC, MAC checked first) is equally sound and hand-verifiable. PBKDF2 iterations are pinned at 10000 — the historical OpenSSL default — precisely so that both very old and very new OpenSSL builds produce identical results.
Why key derivation is sha256(key + ":purpose"). It must be reproducible from one memorized sentence on any machine (Section 5.2). Domain separation (":encryption" vs ":authentication") prevents key confusion; PBKDF2 does the stretching afterwards.
Why 128 GB chunks. Large enough that LTO-9 drives stream at full speed (tape hates small files), small enough that one chunk fits on scratch disk during verification and that a single bad spot on tape costs one chunk, not one tape. 18 TB tape − 0.30 TB headroom fits roughly 138 full 128 GB chunks per cartridge; the headroom guarantees room for the close artifacts and end-of-media margin.
Why whole files inside TAR_PARTs (never split across chunks). A single lost or corrupted chunk then costs only the files inside it, each of which is either fully present or fully absent — no half-files to detect. Only files bigger than a whole chunk are sliced, and those slices are trivial byte-range concatenation.
Why the metadata chunk is last. Directory permissions may be restrictive (read-only frozen datasets). Applying them after all file writes means restoration works for non-root users. This ordering is load-bearing in every restore path — do not reorder it.
Why SQLite + SQL text dumps for catalogs. A single-file, zero-server database whose on-disk format has been stable for 20+ years — and the on-tape catalogs are not even binary SQLite but plain SQL text: readable with human eyes if all else fails, reloadable into any future SQLite (schema shipped alongside as schema.sql).
Why Bash + coreutils + OpenSSL and not a modern language. The recovery-path question is not "what is nicest to write" but "what will still run, unmodified, on whatever Unix exists in 15 years". tar, dd, mt, awk, sha256sum and openssl are the safest such bet. (The operational side pays a real cost for this choice in review effort — accepted deliberately.)
Any OpenSSL 1.1.1 or later recovers these tapes — no specific version, no module. Every encryption parameter is pinned in the recipe itself (-aes-256-cbc -pbkdf2 -iter 10000 -salt), so a blob written under one OpenSSL opens under any other that is given those parameters. Verified in both directions between 1.1.1 and 3.x. The production nodes run OpenSSL 3.x (loaded via an environment module) for day-to-day operations — bus-marker signing needs a working openssl dgst — but that module is an operational convenience, never a prerequisite for recovery. If you are reading this to recover data, do not hunt for a particular OpenSSL build or a module: use whatever openssl the system has.
Why a file bus with rename-claims instead of a network service. No daemons to version, no protocols to keep compatible, no auth infrastructure; the concurrency primitive is POSIX rename atomicity, which is inspectable with ls. The trade-off — the shared filesystem must actually honor the POSIX properties — is documented and was verified for the deployed hardware.
Why the TOC contains no user file names. The TOC is plaintext on the tape; a stranger holding the cartridge learns only chunk counts, run identifiers and hashes. All names live inside the user-key-encrypted project catalog. Enforced with a write-time guard, not just policy.
Why the quiescence guard exists (size+mtime, not inode). Slices of one large file may be produced hours apart by different jobs; a source mutating in between would land on tape as a silent mix of versions detectable only years later. Recording size+mtime at planning and re-verifying before and after each production turns that into an immediate abort. The inode is deliberately excluded: it legitimately changes under snapshots and storage migrations and would only generate false alarms.
Why hard links are NOT deduplicated. Handling links across independently encrypted chunks would couple chunks together, breaking invariant 3. The cost is tape space (each link archived as an independent file) — space is cheaper than coupling.
Why "never a second implementation of the same thing". Two almost-equal code paths diverge, and the bug is born where they diverge — this project removed a duplicate restore script after exactly that incident, and later found a real identifier-format divergence between the daemon and the catalog rebuilder. The one accepted duplication is the DR tool's self-contained escrow-unwrap, because DR must run with zero infrastructure; it is flagged to be modified in lockstep with the canonical copy.
Why optional hardening defaults to OFF. ECDSA P-256 signing of bus markers and replay protection exist for a hostile-peer-on-the-share threat model. They default off (require_bus_signing=0) so they do not tax the mental model of deployments without that threat. The rule generalizes: hardening must never complicate the recovery story.
Why every feature must attach to an invariant or an observed failure. The long-term risk of this system was judged to be complexity, not code: an innocent-looking change breaking an invariant elsewhere years later. The extension rule makes every addition justify its cognitive cost — and makes unattached code a removal candidate by construction.

SECTION 12Failure modes and graceful degradations

SituationWhat still works, and how
One tape of a pair lost / destroyed / unreadableFull recovery from the other tape. Every chunk and every catalog exists on both.
A chunk copy fails its SHA/HMAC on one tapePer-chunk fallback to the partner tape ("auto-healing"). Only if BOTH copies of the SAME chunk are bad is that chunk lost — and then only the whole files inside that one chunk.
The last TOC's header is corruptedThe backward scan skips it and uses the previous TOC (TOCs are cumulative). You lose visibility only of what was archived after that older TOC — and only if the partner tape's TOC is also gone.
A TOC's header is intact but its body is damagedMalformed lines are skipped silently — entries can vanish without an error. Mitigations: the partner tape's own TOC, and the placement table inside the encrypted project catalog, an independent second source for the same mapping (and each catalog's SHA-256 is recorded in the partner tape's TOC). A self-checksummed TOC trailer is deferred to FORMAT-V2.
A later run was writing when disaster struckIts chunk blobs sit after the last TOC; the backward scan walks past them. The interrupted run is simply absent; every closed run is fully recoverable.
Both operational databases lost (cluster + tape server)By design, irrelevant to data recovery (Sections 6–8). To resume operating: bric-tape-rebuild-catalog.sh --verify reconstructs the tape database from the TOCs; tests assert a rebuilt catalog is operationally indistinguishable.
User key lostBreak-glass via master key + escrow (Section 8) — if and only if escrow was enforced at that user's registration.
Master key lostUser-key recovery of each project still works (Section 7). Only the institutional break-glass path is gone; user-key recovery remains intact.
BOTH keys lostThe data is gone. AES-256 with a 256-bit random secret has no shortcut. This is stated plainly because the keys are the single true point of failure: guard the key escrow and the master key with institutional seriousness.
"bad decrypt" from opensslWrong key, wrong derivation (check the literal suffixes and that -pbkdf2 -iter 10000 are present), or corrupt input (check the SHA first — that is why it exists).
Recovered file fails its plaintext SHA-256For a large file: one slice came from a bad copy — redo just that slice from the partner tape. For a TAR_PART file: re-extract that chunk from the partner copy. If a source was modified during archiving in the pre-guard era, the mix is detected here.
LTO-9 drives extinct in your eraThe format needs only: position to file N, stream 256 KiB blocks until filemark. Any future device or service that can produce a raw dump of tape files can feed Section 7. Migrate media proactively every ~10 years while drives are common.

SECTION 13Verifying a recovery — the chain of proof

The format carries four independent layers of proof. A recovery is complete when all four pass:

  1. Tape-file integrity: SHA-256 of each raw tape file equals its TOC entry (keyless — anyone can check).
  2. Authenticity: HMAC-SHA256 of each blob equals chunks.payload_hmac (proves it was produced by the key holder and untouched since).
  3. Decryption success: OpenSSL padding + tar structural validity (weak alone; meaningful after 1–2 pass).
  4. End-to-end content: SHA-256 of every recovered file equals files.sha256_plain, recorded at archive time from the original data. This is the proof that matters: bit-identical to what the scientist archived.

Never skip layer 2 to save time, and never treat layer 3 alone as success.

SECTION 14Glossary

Terms are also explained in hover tooltips throughout the document (dotted underlines). Here they are in full, alphabetically.

Append-only
A medium or policy where data is only ever added after the existing end, never modified or deleted in place. All BRIC tapes are append-only: history is physically preserved.
Blob
An opaque encrypted file — here, the on-tape/on-bus form of a chunk: Salted__ header + AES-256-CBC ciphertext.
Break-glass
An emergency recovery path meant for exceptional use: the institution's master key unlocking an escrowed copy of a user key (Section 8).
Bus (QNAP bus)
The shared network directory through which the cluster and the tape server exchange chunk blobs and marker files. All coordination is file creation and atomic renames — no sockets, no RPC. Hosted on a QNAP NAS over NFS in the deployed system.
CBC (Cipher Block Chaining)
A classic AES mode providing confidentiality only. Integrity comes from the separate HMAC, verified first (Encrypt-then-MAC).
Chunk
The unit of archiving (128 GB): either a tar stream of whole files (TAR_PART) or a byte-range slice of one oversized file (LARGE_FILE_CHUNK). Independently encrypted, authenticated and restorable — the heart of invariant 3.
Catalog
The database describing what was archived and where. New tapes carry the user-key-encrypted project catalog, a small master-wrapped user-key escrow, and the plaintext schema/recovery kit. Legacy tapes may also contain a master-encrypted whole-system catalog.
Daemon (bric-tape-daemon)
The single long-running process on the tape server that claims chunks from the bus, writes and verifies both tape copies, and seals runs with catalogs and a TOC.
DR (Disaster Recovery)
Recovering data from the tapes and one key alone, with no databases, daemons or infrastructure. The scripted form is bric-dr-from-tapes.sh; the manual form is Section 7.
EOD (End Of Data)
The position after the last written block on a tape (mt eod). All writes append here.
Escrow (key escrow)
An encrypted, HMAC-authenticated copy of a user key, wrapped with the master key and stored in users.key_escrow (format v2:<hmac>:<base64>). New closes copy this ciphertext into project-bound user_key_escrow.v1; no master operation occurs in the user job.
Encrypt-then-MAC
Encrypt first, then compute a MAC over the ciphertext; verifiers check the MAC before decrypting. The composition used for every blob and escrow in this system.
Filemark
A hardware end-of-file marker separating tape files. In BRIC on Linux it is written automatically when dd closes the non-rewinding tape device after a write; an extra mt weof must not be added. dd reads stop at it; mt fsf N skips N of them.
HMAC (HMAC-SHA256)
A keyed checksum: only a key holder can produce a valid one, so it proves both integrity and authenticity. Computed here over ciphertexts and verified before any decryption.
Isilon
The NFS storage cluster holding the live source data in the original deployment. Irrelevant to recovery.
LTO (Linear Tape-Open)
The open, multi-vendor magnetic tape standard. These cartridges are LTO-9: 18 TB native, ~30-year media rating. Drives read at least one generation back.
Marker
A tiny text file on the bus whose name encodes state (chunk_0001.READY, .CLAIMED, .DONE, .ERROR, run.ABORTED…) and whose content carries key=value fields, optionally ECDSA-P-256-signed (format BRIC-MARKER-V1). State transitions are atomic file renames.
Master key
The institution's one-line secret (32 random bytes, base64), kept administrative/offline. It unwraps authenticated user-key escrows and cannot decrypt data directly. New user jobs never read it; catalog_system.enc is a legacy format only.
Metadata chunk
The final TAR_PART of every run: all directories (including empty ones) with their permissions and mtimes, plus symlinks. Always restored LAST, because its permissions may be restrictive.
Pair (tape pair)
Two cartridges written as mirrors: the even-barcode PRIMARY (onsite) and the odd-barcode BACKUP = PRIMARY+1 (offsite when full). Either alone normally suffices for recovery.
PBKDF2
Password-Based Key Derivation Function 2: stretches a passphrase and salt into the AES key and IV. Iteration count pinned at 10000 in every command line, forever.
Placement
The table inside the project catalog mapping each chunk copy to a tape and tape-file number: run_id, chunk_no, copy_role, volumetag, file_number.
PRIMARY / BACKUP
The two roles of a tape pair: PRIMARY (even barcode, onsite) is written and read first; BACKUP (odd, offsite when full) is the per-chunk fallback.
Quiescence (source quiescence)
The requirement that source data not change between planning and production. Enforced by recording size+mtime at planning and re-verifying before and after each chunk is produced; drift aborts the run.
Run
One complete execution of "archive this project now", identified as <project>__<UTC timestamp>__<counter> (e.g. mouseproj__20260708T101500Z__0003). Lexicographic order equals chronological order — a property recovery relies on when the same file exists in several runs (latest wins).
Salt
8 random bytes mixed into PBKDF2 so identical plaintexts encrypt differently. Embedded in each blob's Salted__ header; never needs separate storage.
Segment / seg_id
One physical copy of one chunk on one tape, identified as <run_id>__c<chunk zero-padded to 4>__<PRIMARY|BACKUP> in the tape database. States: WRITING → VERIFIED (or ABANDONED after a crash).
SHA-256
The cryptographic hash used everywhere: tape-file integrity (in the TOC), plaintext file identity (files.sha256_plain), key derivation, and inside HMAC.
SLURM
The HPC batch scheduler that ran chunk producers in parallel on the cluster. Irrelevant to recovery.
tar
The POSIX tape-archive format (GNU tar). TAR_PART chunks decrypt to plain tar streams; extraction uses -xp --no-same-owner --delay-directory-restore and never -P (path-traversal safety).
TOC (TAPE_TOC.txt)
The cumulative plaintext index appended to a tape after every close: header # BRIC tape TOC v1 plus pipe-separated lines mapping tape-file numbers to chunks/artifacts and their SHA-256 (Section 4). The last valid TOC on a tape wins.
User key
A data owner's one-line secret (32 random bytes, base64), issued at registration. With it, that owner's data is recoverable from the tapes alone, forever.
Variable-block mode
The drive mode (mt setblk 0) in which each write() is one tape block. This archive uses 262144-byte (256 KiB) blocks: always read with dd bs=262144.
Volumetag / barcode
The cartridge's 8-character label, NNNNNNL9. Even digits = PRIMARY, odd = BACKUP (= PRIMARY+1). The database and TOC identify tapes by it.
WAL
SQLite's Write-Ahead Logging journal mode, used by the operational databases for crash safety. Irrelevant to the on-tape format.
